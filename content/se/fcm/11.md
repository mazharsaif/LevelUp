## 11. Use it, or not?

After this skill you can look at any app idea and decide whether Firebase fits it, fits part of it, or does not fit at all. You will know the honest limits of Firestore, the main alternatives, and five questions to ask before you commit.

### Signals for and against

Firebase is a good choice when most of these are true:

- **A small team.** One to a few people who want to write the app, not run servers.
- **A mobile or web app** that talks to the data directly through the SDK.
- **Document-shaped data.** Each screen reads a few small records that belong together, like one user's notes.
- **Real-time or offline needs.** Screens that update live, or an app that must keep working on a train with no signal.
- **No backend to run.** Sign-in, rules and a few functions cover the server work.

Firebase is a weak choice when these appear:

- **Relational data and SQL reporting.** Many tables linked to each other, and people who ask questions like "revenue per region per month, minus returns".
- **An existing backend that works.** Moving working code to a new platform costs months and brings little.
- **Strict portability or data-residency rules.** **Data residency** means the law or a contract says where data must be stored. You choose a Firestore location once, when you create the database, and you cannot change it later. **Portability** means you can move to another provider without a rewrite; much Firebase code is tied to Firebase.
- **Unpredictable read patterns.** Firestore bills per document read. A screen that scans thousands of documents, or a feature whose use you cannot predict, makes the bill hard to predict too.
- **Heavy server-side compute.** Video processing, long imports or machine learning jobs. Cloud Functions have time and memory limits; long jobs belong on a server or a container service.

One strong "against" signal can outweigh three "for" signals. A tool for accountants that needs SQL reports is a poor fit even if the team is small.

### Honest limits of Firestore

Firestore is fast and simple for the queries it was built for. Know where it stops.

- **No joins.** In the standard edition, one query reads one collection (or one collection group). To show a note with its author's name, you either copy the name into the note or make a second read. See Firestore data.
- **Limited queries.** Every query needs an index. Some filter and sort combinations need a composite index that you create first. You cannot ask "anything you like" the way SQL allows.
- **Aggregation exists, with limits.** Firestore can count, sum and average on the server. You pay one read for each batch of up to 1,000 index entries scanned. These queries do not work with live listeners or offline.
- **Full-text search is not part of the standard edition.** Searching inside note text means an extension that copies data to a search service, or the newer **Enterprise edition** of Firestore, which offers text search and join-like steps through **pipeline queries** (a newer query style built from stages). Text search in Enterprise edition has been in preview, so check its current status, pricing and plan rules before you choose it.

Here is a native count of one user's notes:

```js
import {
  collection, query, where,
  getCountFromServer
} from "firebase/firestore";

// Count one user's notes
const q = query(
  collection(db, "notes"),
  where("ownerId", "==", uid)
);
const snap =
  await getCountFromServer(q);
console.log(snap.data().count);
```

If you need relational data but like the rest of Firebase, look at Firebase SQL Connect (formerly Data Connect). It gives you a managed PostgreSQL database inside a Firebase project.

### The alternatives

No tool is best for everything. This table compares the common choices fairly.

| Option and best when | Breaks when | Effort |
|---|---|---|
| **Own backend**: you need full control or have one already | Small team must also run servers | High |
| **Supabase**: you want PostgreSQL, SQL and open source | You need deep mobile extras like Crashlytics | Medium |
| **Appwrite**: you want an open-source suite to self-host or use as a service | Your team cannot operate it, or needs rare features | Medium |
| **PocketBase**: one small server, one file, a side project | You need many servers or a long-term stable API | Low |
| **Cloud mobile backend** (for example AWS Amplify): you already use that cloud | You do not know that cloud's other services | Medium |

A few notes on the table:

- **Supabase** is built on PostgreSQL, so joins, SQL reports and normal database tools work.
- **Appwrite** and **PocketBase** can run on your own server. That helps with residency and portability, but then you own the updates, backups and uptime.
- **PocketBase** is a young project. Check how stable its versions are before you rely on it, because upgrades of young projects can break things.
- An **own backend** is the most work at the start and the least lock-in later.

### Adopt only one piece

Firebase is not all or nothing. Each product works on its own, and many teams use just one.

Common single pieces:

- **Only push (Cloud Messaging).** Your own server keeps users and data. It stores push tokens in its own database and sends messages with the Admin SDK.
- **Only Hosting.** A fast home for a static website, with free HTTPS.
- **Only Crashlytics or Analytics** inside a mobile app that has its own backend.
- **Only Auth** in front of your own API, which verifies ID tokens. See Sign-in (Auth).

Pieces differ in how hard they are to leave:

| Piece | To leave | Why |
|---|---|---|
| Hosting | Easy | Static files move anywhere |
| Push | Easy | Only the send code changes |
| Analytics | Easy | You lose old charts |
| Auth | Medium | Users export, sign-in code changes |
| Firestore | Hard | Data model, rules, listeners |

Firestore is the hard one because the app calls it from every screen, the security rules are written for it, and live listeners have no direct copy elsewhere. Before you build on Firestore, decide that you are happy to stay, or keep all data access in one module of your code so that a move touches one place. The exit plan in Costs & safety covers this.

### Four scenarios

**A habit tracker for friends.** Each person ticks habits each day and sees friends' streaks live. **Verdict: good fit.** Data is small and per person, live updates matter, offline ticks are useful, and the team is one person. The free plan likely covers it. Copy each streak count into a small shared document so friends' screens do not read every tick.

**An internal reporting tool.** Staff want monthly reports across customers, invoices and products. **Verdict: poor fit.** The data is relational, the questions are SQL questions, and each report would read thousands of documents. Use a SQL database with a reporting tool. If the team wants Firebase anyway, use SQL Connect, not Firestore.

**A shop with orders and stock.** **Verdict: possible, with care.** Products and order history fit documents. Stock needs **transactions** (a group of writes that all succeed or all fail), which Firestore supports. Payments must be handled in a function, never in the client. Sales reports need an export to an analytics database. For many small shops a ready-made shop platform is less work than any custom build.

**An existing website that only needs push.** **Verdict: use one piece.** Keep the current backend. Add the Firebase Messaging SDK and a service worker to the site, save tokens in the existing database, and send from the existing server with the Admin SDK. Do not move any data into Firestore. The standard Web Push protocol without Firebase is also an option for web-only sites.

### Try it

This is a thinking exercise. It takes about ten minutes.

Take the Notes app and answer the five questions below. Then do the same for an app idea of your own.

1. What shape is the data, and which reports will be needed in a year?
2. What is the most used screen, and how many reads does it cost per user per day?
3. Are there rules on where data must live, or a need to move providers later?
4. What work must run on a server, and how long does each run take?
5. If you had to leave, which pieces would you rewrite, and how long would it take?

For the Notes app you should reach answers close to these. The data is per user documents and no one needs cross-user reports. The note list reads one document per note shown, so a limit of 50 per screen keeps costs small. Pick the Firestore location near your users on day one. Server work is short: one reminder function. Leaving means rewriting the data layer and the rules, so keep Firestore calls in one file. Verdict: a good fit.

If your own idea has two or more "hard" answers, compare it with one alternative from the table before you start.

### Common mistakes

- **Choosing by popularity.** You pick Firebase because tutorials use it. What you see: months later, reports and joins are painful. Fix: run the five questions first.
- **Ignoring read cost on busy screens.** A dashboard reads every document on each open. What you see: a bill that grows faster than users. Fix: estimate reads per screen; store totals in summary documents.
- **Moving a working backend to Firebase.** What you see: a long rewrite with no new features. Fix: adopt only the piece you need, such as push.
- **Choosing the wrong location.** What you see: slow responses, or a residency rule broken. Fix: pick the location on purpose; it cannot be changed later.
- **Spreading Firestore calls through every file.** What you see: leaving becomes a full rewrite. Fix: one data module that the screens call.

### Check yourself

1. A team of two wants a live chat app that must work offline. Name two signals that point to Firebase.
2. Why is an internal reporting tool a poor fit for Firestore?
3. Which Firebase piece is hardest to leave, and why?
4. A working website needs push. What do you move into Firestore?

**Answers.** 1. Small team, real-time updates, offline needs, and no backend to run (any two). 2. The data is relational and the questions need joins and SQL, while Firestore has no joins in its standard edition and bills per document read. 3. Firestore, because its data model, rules and live listeners are spread through the app and have no direct copy elsewhere. 4. Nothing; keep the existing backend and data, and use only Cloud Messaging with tokens saved in the existing database.
