## 6. Pitfalls & costs

This skill lists the mistakes real teams make with Firebase, the cost guardrails to set up early, and how to plan an exit.

### Eight mistakes

1. **Shipping open rules ("test mode").** Symptom: anyone with your app's public config can read or wipe the database. Fix: start from deny-all, write per-collection rules, test them in the emulator, add App Check.
2. **Mixing up the config file and the service-account key.** Symptom: panic over `google-services.json`, or a key committed to git. Fix: the config file only identifies the project; the service-account key is the secret.
3. **A query that reads everything.** Symptom: a surprise bill when a screen reads thousands of documents. Fix: paginate, `limit`, avoid listeners on huge collections, estimate reads per screen.
4. **Designing the data like SQL.** Symptom: you need a join and cannot do one. Fix: design around screens, duplicate on purpose, or pick a relational backend.
5. **Trusting the client with the rules of the game.** Symptom: users edit their own score, role or balance. Fix: make those fields writable only by trusted code.
6. **Notification messages and dead tokens.** Symptom: no code runs in the background; errors and duplicates pile up. Fix: use data messages, delete tokens on `UNREGISTERED`, and keep the truth in your database.
7. **Adopting the whole platform for one piece.** Symptom: two databases, two logins, a migration nobody wants. Fix: choose per product.
8. **Ignoring that phones and plans change.** Symptom: pushes never arrive on some brands, or a feature moves behind a paid plan. Fix: test on real devices and re-check pricing before launch.

### Billing guardrails

Do these on day one if you use Blaze:
- Create a budget with alert thresholds in Google Cloud Billing. Alerts notify you; they do not stop spending.
- Put `limit` on every query.
- Add App Check so scripts cannot hammer your database or SMS sign-in.
- Watch the usage dashboard in the first week of any release.
- A hard stop has to be built by you (for example a function that disables billing on an alert), which is advanced and can take the app down. [consensus, fast-moving]

### Exit strategy

Decide before you need it. You can export Firestore data to a bucket and on to BigQuery, export users with `firebase auth:export`, and keep Storage files, which are ordinary Google Cloud Storage objects. [verify the current export docs]

The hard parts are yours to write: a new query layer, rules rebuilt as backend authorization code, and password hashes (a Firebase-specific scrypt variant). A test before adopting any root product: "if I had to leave in six months, what would I rewrite?" If the answer is "everything", that is the lock-in price.

### The phone is the hidden tax

Push has its own failure mode: aggressive battery managers on some phone brands delay or drop pushes for apps that are not whitelisted. You cannot fix that from the server. Use a short TTL, keep payloads small and free of secrets, and test on the phones your users actually have.
