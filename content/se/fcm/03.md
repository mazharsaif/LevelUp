## 3. Sign-in (Auth)

After this skill you can let people create an account in the Notes app, sign in with email or Google, and sign out. You will also know what the uid is, how your own server can trust a signed-in user, and what sign-in costs.

### What Firebase Auth does for you

**Firebase Authentication** (Auth for short) is the Firebase product that checks who a person is. It stores accounts, checks passwords, talks to Google and other sign-in providers, and keeps the user signed in between visits. You never store a password yourself.

A **sign-in provider** is one way to prove who you are: email and password, Google, Apple, a phone number, and others. You switch each one on in the Firebase console, under Authentication, on the Sign-in method tab. A provider that is off will refuse every attempt.

When a person signs in, Auth gives them a **uid** (user id): a long random string such as `kT3x9...`. It never changes for that account, even if the person changes their email or name. This makes it the key to everything else in the Notes app:

- each note stores `ownerId: uid`
- each person's profile lives at `users/{uid}`
- each person's photos live at `photos/{uid}/...`
- the security rules compare the uid of the caller with the `ownerId` of the data (see Security rules)

Never use the email as the key. Emails change, and they are personal data you do not want inside every document path.

The client code uses the modular web SDK. To keep lines short on a phone, the examples rename long function names with `as`. That is plain JavaScript and changes nothing else.

### Email and password

Switch on the Email/Password provider first. Then:

```js
import {
  getAuth,
  createUserWithEmailAndPassword
    as signUp,
  signInWithEmailAndPassword
    as signIn,
  sendEmailVerification,
  sendPasswordResetEmail,
} from "firebase/auth";

const auth = getAuth(app);
```

Sign up creates the account and signs the person in at once:

```js
const cred = await signUp(
  auth, email, password);
// Ask them to confirm the address
await sendEmailVerification(
  cred.user);
```

Sign in later:

```js
try {
  await signIn(auth, email, password);
} catch (e) {
  // e.code, for example
  // "auth/invalid-credential"
  showError("Sign-in failed");
}
```

Each error has a `code` such as `auth/email-already-in-use` or `auth/weak-password`. Show a short, friendly message, not the raw code. For sign-in, show the same message whether the email or the password was wrong, so nobody can test which emails have accounts.

**Email verification** means the person clicks a link sent to their address. After that, `user.emailVerified` is `true`. Auth does not block unverified users by itself; you decide, for example "you can write notes, but you cannot share them until you verify".

For a forgotten password, one call sends a reset link:

```js
await sendPasswordResetEmail(
  auth, email);
```

### Google sign-in and anonymous accounts

Switch on the Google provider, then:

```js
import {
  GoogleAuthProvider,
  signInWithPopup,
} from "firebase/auth";

const provider =
  new GoogleAuthProvider();
const res = await signInWithPopup(
  auth, provider);
console.log(res.user.uid);
```

A popup opens, the person picks a Google account, and the popup closes. On small phone screens a full-page redirect (`signInWithRedirect`) can work better than a popup. Redirects need extra setup on some browsers; follow the redirect best practices in the docs under Authentication.

An **anonymous account** is a real account with a uid but no email or password. Use it to let people try the app before they commit:

```js
import { signInAnonymously }
  from "firebase/auth";
await signInAnonymously(auth);
```

Their notes are saved under that uid. Later, when they choose a password, you **link** the new sign-in method to the same account, so the uid and all notes stay:

```js
import {
  EmailAuthProvider,
  linkWithCredential,
} from "firebase/auth";

const c = EmailAuthProvider
  .credential(email, password);
await linkWithCredential(
  auth.currentUser, c);
```

The cost: if an anonymous user signs out or clears the browser, that account and its notes are lost to them. Anonymous accounts also pile up. With the upgrade to Identity Platform (an optional paid upgrade of Auth), you can turn on automatic clean-up of old anonymous accounts.

### Auth state and sign-out

Sign-in state survives page reloads. When the page opens, Auth needs a moment to restore the user, so `auth.currentUser` is `null` at first, even for a signed-in person. Do not read it at start-up. Listen instead:

```js
import {
  onAuthStateChanged,
  signOut,
} from "firebase/auth";

onAuthStateChanged(auth, (user) => {
  if (user) {
    showNotes(user.uid);
  } else {
    showSignInScreen();
  }
});
```

This callback runs once when the state is known, and again every time someone signs in or out. Make it the single place that decides which screen to show. Then sign-out is one line, and the listener moves the person back to the sign-in screen:

```js
await signOut(auth);
```

When a user signs out, also stop any live data listeners you started for them (see Firestore data), or they will fail with permission errors.

### ID tokens and your own server

Firebase products such as Firestore know who the caller is by themselves. Your own server does not. If the Notes app calls your own API, for example to export notes as a file, the server must check who is asking.

An **ID token** is a short signed message from Auth that says "this is uid X", in a standard format called a **JWT** (JSON Web Token). It lasts one hour; the SDK renews it for you. The client sends it with each request:

```js
const token = await auth.currentUser
  .getIdToken();
await fetch("/api/export", {
  headers: {
    Authorization: `Bearer ${token}`,
  },
});
```

The server checks the signature with the **Admin SDK** (the Firebase library for trusted servers). Node.js:

```js
import { initializeApp }
  from "firebase-admin/app";
import { getAuth }
  from "firebase-admin/auth";

initializeApp();

async function uidOf(req) {
  const h =
    req.headers.authorization || "";
  const token = h.replace(
    "Bearer ", "");
  // Throws if fake or expired
  const d = await getAuth()
    .verifyIdToken(token);
  return d.uid;
}
```

Python does the same with `auth.verify_id_token(token)` from `firebase_admin`. Never trust a uid that the client sends as plain text; trust only the uid inside a verified token. Verification does not check whether the account was disabled a minute ago. If that matters, pass `checkRevoked` as `true` in Node (`check_revoked=True` in Python); it costs an extra network call.

### Limits, costs and leaving

Email, Google and anonymous sign-in are free up to a daily number of active users on the Spark plan; check the Authentication limits and pricing pages for the current numbers. Auth also limits how many accounts one IP address can create per hour, which slows down bots.

**Phone sign-in** sends a code by SMS. Each SMS is billed, it needs the Blaze plan, and prices differ by country. Attackers sometimes trigger thousands of SMS to expensive numbers to earn money from them, so if you use it, limit the countries that may receive codes and set a budget alert (see Costs & safety).

**Lock-in** means how hard it is to leave. To move away from Firebase Auth you would:

- export users with `firebase auth:export`
- move password hashes, which use a modified scrypt; your new system must support it, or users must reset passwords
- keep the same uids, or rewrite every `ownerId` and path
- change your server to verify the new tokens

It is possible, but plan it before you have many users.

### Try it

You will create a user in the **Auth emulator**, the local copy of Auth that runs on your computer for free. Use the project folder from Project & plans, where `firebase init emulators` added Auth.

1. Start it: `firebase emulators:start --only auth`
2. In a new folder, run `npm init -y` and `npm install firebase`.
3. Save this as `lab.mjs`:

```js
import { initializeApp }
  from "firebase/app";
import {
  getAuth, connectAuthEmulator,
  createUserWithEmailAndPassword
    as signUp,
} from "firebase/auth";

const app = initializeApp({
  apiKey: "demo-key",
  projectId: "notes-demo",
});
const auth = getAuth(app);
connectAuthEmulator(auth,
  "http://127.0.0.1:9099");

const c = await signUp(auth,
  "ana@example.com", "secret123");
console.log("uid:", c.user.uid);
```

4. Run `node lab.mjs`. You should see a uid printed.
5. Open the Emulator UI at `http://127.0.0.1:4000`, then the Authentication tab. Ana is listed with the same uid.
6. Run the script again. It fails with `auth/email-already-in-use`. Change the email and it works.

### Common mistakes

1. **Reading `currentUser` at start-up.** You see `null` and the app shows the sign-in screen to a signed-in user. Fix: use `onAuthStateChanged`.
2. **Provider not switched on.** You see `auth/operation-not-allowed`. Fix: enable it on the Sign-in method tab.
3. **Using the email as the key.** A user changes email and loses all notes. Fix: key everything by uid.
4. **Server trusts a uid from the request body.** Anyone can claim any uid. Fix: verify the ID token with the Admin SDK.
5. **Phone sign-in with no limits.** A large SMS bill. Fix: limit countries and set a budget alert.

### Check yourself

1. Why should `ownerId` hold the uid and not the email?
2. Your app shows the sign-in screen for a moment after every reload. What is wrong?
3. A guest wrote notes with an anonymous account and now wants a password. What do you call, and why?
4. Your server gets `{ "uid": "abc" }` in a request. Why is that not enough?

**Answers.** 1. The uid never changes and is not personal data; emails change. 2. The code reads `auth.currentUser` before Auth has restored the user; decide screens inside `onAuthStateChanged`. 3. `linkWithCredential` with an email credential, so the uid and the notes stay the same. 4. Anyone can send any uid; the server must verify an ID token with the Admin SDK and use the uid inside it.
