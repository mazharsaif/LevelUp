## 1. Why Firebase exists

After this skill you will know what problem Firebase solves, which of its products do what, and what you give up when you use it. You will also see the Notes app you will build, piece by piece, in the rest of the course.

### The work before your first user

Say you want to build a small **Notes app**. People sign in, write notes, attach a photo, and get a reminder on their phone. The screens are the fun part. But before one real person can use it, someone has to build a **backend**: the computers and code that run on the internet, not on the user's phone.

Here is what that backend must do:

- **Sign-in.** Store passwords safely (hashed, never plain text), send reset emails, support "Sign in with Google".
- **A database.** Store every note, and make sure one user can never read another user's notes.
- **File storage.** Keep photos somewhere safe and fast to download.
- **An API.** A set of web addresses your app calls to read and write data, with checks on every call.
- **Push notifications.** Send a reminder to the right phone, even when the app is closed.
- **Hosting.** Serve your web pages over HTTPS (the secure version of the web protocol).
- **Operations.** Backups, security updates, scaling when traffic grows, logs when something breaks.

Each item is a small project. Together they can take weeks before you write a single screen. And after launch, someone must keep the servers patched and running at 3 a.m.

Most small teams do not want to be in the server business. They want to build the app. Firebase exists for exactly this gap: it gives you ready-made, hosted versions of the common backend parts, so your app can talk to them directly.

### What Firebase is, and is not

**Firebase** is a platform from Google that gives app developers ready-made backend services. You create a **project** (one container for all the services and data of one app) and connect your app to it.

Your app talks to Firebase through an **SDK** (software development kit: a library you add to your code). Instead of writing an API, you call functions such as `addDoc()` to save a note. The SDK sends the request to Google's servers.

This style is often called **Backend as a Service**: the provider runs the servers, and you configure them.

What Firebase **is**:

- A set of separate products that work well together. You can use one, or many.
- Built on **Google Cloud**. Every Firebase project is also a Google Cloud project, so you can add other Google Cloud services later.
- Client-first. Phones and browsers often talk to the database directly, protected by **security rules** (rules that decide who may read or write your data).

What Firebase **is not**:

- Not a server you log into. You cannot install your own software on it.
- Not a classic SQL database. The main database, Firestore, stores documents, not tables with joins.
- Not free without limits. There is a free plan, but heavy use costs money.
- Not a replacement for careful design. A badly written rule can still expose all your data.

You still write code that must run in a trusted place, such as sending a push message. For that, Firebase offers **Cloud Functions**: small pieces of your code that Google runs when something happens.

### The product catalogue

Firebase has many products. These are the ones this course uses, grouped by job.

#### Build the app

| Product | What it does | In the Notes app |
|---|---|---|
| Authentication | Sign-in and user ids | Email and Google login |
| Cloud Firestore | Document database | The `notes` collection |
| Cloud Storage | Stores files | Note photos |
| Cloud Functions | Runs your server code | Sends reminders |
| Hosting | Serves web pages | The web app itself |
| Cloud Messaging | Push notifications | Reminder alerts |

#### Run and improve the app

| Product | What it does | In the Notes app |
|---|---|---|
| Analytics | Counts user actions | How many notes per day |
| Crashlytics | Reports app crashes | Find bugs fast |
| Performance | Measures speed | Slow photo uploads |
| Remote Config | Change settings live | Turn a feature on |
| App Check | Blocks fake clients | Only your app may call |

Other products exist, for example Realtime Database (an older database), Data Connect (a PostgreSQL database), App Hosting (for server-rendered web apps) and AI features. You can add them later; the ideas in this course still apply.

### How a request flows

When a user saves a note, this is what happens:

```text
 Phone or browser (your app)
   |  SDK call + ID token
   v
 +------------------------------+
 | Firebase (Google servers)    |
 |  1. Auth: who is this?       |
 |  2. Rules: is this allowed?  |
 |  3. Firestore: save the note |
 +------------------------------+
   |  event (optional)
   v
 Cloud Function (your code)
   |  send message
   v
 Cloud Messaging -> user phone
```

1. The app calls the SDK. The SDK attaches an **ID token**, a short-lived signed proof of who the user is.
2. Firebase checks the token, then checks your security rules.
3. If the rules allow it, the note is saved. Other open screens can see the change at once.
4. If you wrote a function for this event, Google runs it. It can, for example, schedule a push reminder.

Notice what is missing: there is no server of yours in the middle. That is the main idea. It is also the main risk, because your rules are now the only guard on your data. See Security rules.

### The trade-offs

Every benefit has a cost. Know them before you start.

| You gain | You pay with |
|---|---|
| Fast start, no servers | Less control |
| Scales on its own | Bills grow with use |
| Live updates built in | Firestore query limits |
| One vendor for all | Lock-in |

**Speed versus control.** You can have sign-in and a database working in an afternoon. But you cannot tune the database engine, run any query you like, or choose exactly how data is stored. Firestore cannot join two collections in one query, so you design data around the screens you show. See Firestore data.

**Cost model.** You pay per read, per write, per stored gigabyte and per download, not per server. Small apps often cost nothing. A bug that reads the same data in a loop can cost real money in a day. See Costs & safety.

**Lock-in.** Your app code calls Firebase functions directly, and Firestore has its own data model. Moving to another provider later means rewriting those parts and exporting your data. Keep that cost low: put Firebase calls in a few files, not spread over every screen.

**When not to use it:** you need complex reports with joins across many tables, strict rules about where data lives that Firebase cannot meet, or a large existing backend that already works. See Use it, or not?.

### Try it

This is a thinking exercise. You need paper or a notes file, about 10 minutes.

1. Pick an app idea of your own, or use the Notes app.
2. Write down every backend job it needs. Use the list from the first section: sign-in, database, files, API, push, hosting, operations.
3. Next to each job, write the Firebase product from the catalogue that covers it. Write "none" if nothing fits.
4. For each "none", write what you would do instead (for example, a Cloud Function, or another service).
5. Circle the one job where a mistake would hurt most.

For the Notes app, your answer could look like this:

| Job | Product | Risk if wrong |
|---|---|---|
| Sign-in | Authentication | Low, it is managed |
| Notes data | Firestore | High: rules leak |
| Photos | Cloud Storage | High: rules leak |
| Reminders | Functions + FCM | Medium: spam |
| Web pages | Hosting | Low |

Most people circle the database. That is correct: the data is what you must protect, and protecting it is your job, not Google's.

### Common mistakes

1. **Thinking "serverless" means "no backend thinking".** You will see: data that anyone can read, because the rules were left open. Fix: treat security rules as your backend code, and test them (see Security rules).
2. **Putting secret work in the app.** You will see: an admin key or a "send push to everyone" call shipped inside the app, where anyone can copy it. Fix: do trusted work in a Cloud Function or your own server.
3. **Modelling Firestore like SQL tables.** You will see: many small reads to build one screen, slow pages and higher bills. Fix: store data the way each screen reads it (see Firestore data).
4. **Ignoring cost until launch.** You will see: a surprise bill after a loop or a viral day. Fix: set a budget alert early (see Costs & safety).
