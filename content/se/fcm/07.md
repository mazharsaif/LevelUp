## 7. Final review

This is the boss skill: a self-check, a one-page cheat sheet, and where to read next.

### Self-check

Answer out loud before you open the answers.

1. What problem does Firebase solve, and what does it make you give up?
2. Why do security rules matter more than in a normal backend design?
3. You need to show a user their last 20 orders with the product name from another collection. How does Firestore handle that, and what does it cost in reads?
4. Choose between Firebase, Supabase and your own FastAPI with Postgres for: (a) a mobile habit tracker for 500 friends, (b) an analytics-heavy internal tool with SQL reporting, (c) an existing backend that needs push notifications.
5. A teammate says "we sent a push but our handler never fires in the background". Why?
6. What goes wrong if you never delete `UNREGISTERED` tokens, or never set a budget alert?
7. Which Firebase products are hard to leave, which are easy, and why?
8. Does a user need a Google account to receive FCM pushes, and what does an ID token let your own backend do?

**Answers.** 1. It replaces the chores of a backend (login, database, storage, push, hosting, crash reports) with managed services you call directly. You give up control and portability, and for the database and login an easy exit. 2. The client talks to the database directly, so rules are the only authorization layer, and a missing or over-broad rule is a data leak. 3. There are no joins. Either duplicate the product name into each order, or fetch the 20 orders and then read each product (about 40 reads and extra round trips). Denormalising is the usual answer. 4. (a) Firebase: mobile, document-shaped, small scale. (b) Supabase or Postgres: relational data and SQL reporting. (c) Keep your backend and add only FCM. 5. You sent a notification message, which the OS tray shows in the background without calling your handler. Send a data message instead. 6. Dead tokens pile up and slow fan-out with errors and duplicates. With no budget alert, a bug or heavy query can run up a bill unnoticed, because Blaze has no hard cap by default. 7. Hard: Firestore, Authentication and the rules logic, because they become your data and identity. Easy: Hosting and FCM, because swapping them touches only the deploy step or the sender. 8. No: the token comes from the app's Firebase config and Play Services (untested without a signed-in Google account). An ID token is a signed JWT your backend can verify with the Admin SDK to learn which user is calling.

### One-page cheat sheet

- **What it is:** Google's catalogue of managed app services, used directly from the app.
- **Use when:** small team, mobile app, document-shaped data, real-time or offline, no backend to run.
- **Avoid when:** relational data and SQL, an existing working backend, strict portability, unpredictable reads.
- **Key terms:** project and Spark or Blaze; ID token; document and collection; security rules; registration token and data message; App Check; emulator.
- **Gotchas:** never ship open rules; estimate reads per screen and set budget alerts; no joins, so denormalise on purpose; keep trusted values writable only by trusted code; delete dead FCM tokens and keep service-account keys out of git.
- **Rule of thumb:** adopt the leaves (push, hosting, crash reporting) freely, think hard before the roots (Firestore, Authentication), and if you already have a backend take only what it lacks.

### Further reading

1. **Firebase documentation** (firebase.google.com/docs): the primary source. Go deep on Authentication, Firestore security rules and Cloud Messaging.
2. **Firebase pricing plans page** (firebase.google.com/docs/projects/billing/firebase-pricing-plans): what needs Blaze and what is free on both.
3. **Firestore quotas and limits** (firebase.google.com/docs/firestore/quotas): document size, index limits and the free quota.
4. **Firebase Emulator Suite documentation** (firebase.google.com/docs/emulator-suite): how to test rules and functions locally.
