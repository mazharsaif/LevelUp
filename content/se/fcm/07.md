## 7. Push basics

After this skill you will know how a push notification travels from your server to a phone or browser, and why it arrives even when your app is closed. You will ask the user for permission, register a web app for push, save its push address under `users/{uid}/tokens`, and receive messages while the app is open and while it is closed.

### How a push message travels

A **push notification** is a short message that your server sends to a device without the user opening your app. The device shows it as a system alert, for example "Reminder: buy milk". Your app does not send it straight to the phone. It passes through four stops:

```text
your server or function
        |
        v
Firebase Cloud Messaging
        |
        v
OS / browser push service
        |
        v
the app (or its alert)
```

**Firebase Cloud Messaging (FCM)** is the free Firebase service that accepts your message and hands it to the right platform. The next stop belongs to the platform: on Android it is Google Play services, on Apple devices it is the **Apple Push Notification service (APNs)**, and in a browser it is that browser's own push service.

Why does this work when your app is closed? Because your app is not the one listening. The operating system (or the browser) keeps one connection open to its push service for all apps at once. When a message arrives, the system shows the alert itself, or wakes your app for a moment. This is also how push differs from a live Firestore listener, which only works while your app is open.

The cost: you do not control the last stops. The user can turn alerts off, the phone can delay delivery to save battery, and a message can be dropped. Treat push as a signal ("something changed"), never as the only copy of important data.

### The push address of one app install

To send a message to one device, FCM needs an address for that exact install of your app. Firebase has two forms of this address:

- **Registration token**: a long string that FCM gives to one app install. This is the older form. The client call that gets it (`getToken`) is now marked deprecated.
- **Firebase installation ID (FID)**: an id for one app install, managed by the Firebase Installations service. You register it with FCM, then send to it. This is the current, recommended form.

Both behave the same way for you:

- **One per app install, not per person.** A user with a phone and a laptop has two. Your data model must allow many per user.
- **It can change.** Reinstalling the app, clearing browser data, or a routine refresh can give a new one. You must save the new value each time.
- **It is not a user id.** It says nothing about who is signed in. You link it to a user yourself, by saving it under that user's `uid`.

In this course, "token" means the push address in either form. Store each one as its own document in `users/{uid}/tokens`, with the token as the document id, so it is never saved twice.

Users do **not** need a Google account to receive push. Your sign-in can be email and password, or anything else. On Android, the device needs Google Play services. On the web, the browser needs to support push and service workers.

### Asking for permission

No platform lets you send alerts without the user's consent.

- **Web**: the browser shows a "Show notifications?" prompt when you call `Notification.requestPermission()`. If the user clicks Block, you cannot ask again from code; they must change it in the browser settings.
- **Android 13 and later**: notifications need the runtime permission `POST_NOTIFICATIONS`, which you request like camera or location access.
- **iOS**: the user must accept a permission prompt, and you must upload an APNs key from your Apple developer account to the Firebase console.

Ask at a good moment, not on the first screen. In the Notes app, ask when the user sets their first reminder:

```js
// Call this from a button click
async function askPush() {
  const p = await Notification
    .requestPermission();
  // "granted", "denied" or "default"
  return p === "granted";
}
```

Browsers expect this call to come from a user action, such as a click.

### Registering a web app

The web needs two extra pieces.

1. A **service worker**: a small script the browser runs in the background, even when your page is closed. FCM expects a file named `firebase-messaging-sw.js` at the root of your site (for example, in the `public/` folder of your web project).
2. A **VAPID key**: a public key that proves to browser push services that messages come from your project. Create it in the Firebase console under Project settings, Cloud Messaging tab, Web configuration, Web Push certificates, Generate key pair. Copy the public key. It is not a secret.

The current way is `register()` plus `onRegistered()` from `firebase/messaging`. The callback gives you the FID each time it is created or changes:

```js
import {
  getMessaging, register,
  onRegistered
} from "firebase/messaging";

const messaging = getMessaging(app);

onRegistered(messaging, (fid) => {
  saveToken(fid); // next section
});

await register(messaging, {
  vapidKey: "YOUR_VAPID_KEY"
});
```

Do not mix the newer FID calls and the older `getToken` call in the same app. Pick one. New apps should use `register()`.

### Foreground and background messages

What your code sees depends on whether the app is in the **foreground** (the page is open and has focus) or the **background** (another tab or app has focus, or the page is closed).

| State | Who receives it | Alert shown? |
|---|---|---|
| Foreground | `onMessage` in page | No, you decide |
| Background | service worker | Yes, for notification messages |

In the foreground, no system alert appears. Your page gets the message and chooses what to do, such as a small banner inside the app:

```js
import { onMessage }
  from "firebase/messaging";

onMessage(messaging, (msg) => {
  const n = msg.notification;
  showBanner(n.title, n.body);
});
```

In the background, the service worker handles the message. If the message has a notification part, the browser shows the alert for you. If it only carries data, nothing appears unless your handler shows it. Sending push explains these two message kinds.

The modular `onBackgroundMessage` lives in `firebase/messaging/sw` and needs a bundler to build the service worker. Without a bundler, you can load the "compat" scripts in the service worker with `importScripts`, as in the lab below.

### Worked example: saving tokens in the Notes app

When a token arrives, save it under the signed-in user. Use the token as the document id and keep a timestamp, so you can later remove tokens that have not been seen for a long time:

```js
import {
  doc, setDoc, deleteDoc,
  serverTimestamp
} from "firebase/firestore";

async function saveToken(token) {
  const uid = auth.currentUser?.uid;
  if (!uid) return;
  localStorage.setItem("fid", token);
  await setDoc(
    doc(db, "users", uid,
        "tokens", token),
    { platform: "web",
      updatedAt: serverTimestamp() }
  );
}
```

`onRegistered` runs again whenever the FID changes, so this one function also handles **token refresh**. If you use the older `getToken` call, there is no such callback: call it on each app start, save the result if it changed, and refresh about once a month.

On sign-out, delete the token **before** `signOut`, while the user may still write their own data. Otherwise the next person on that laptop gets their reminders:

```js
async function logOut() {
  const uid = auth.currentUser.uid;
  const t = localStorage
    .getItem("fid");
  if (t) await deleteDoc(doc(db,
    "users", uid, "tokens", t));
  localStorage.removeItem("fid");
  await signOut(auth);
}
```

Protect `users/{uid}/tokens` with security rules so only that user can read or write it (see Security rules). Other users should never be able to read someone's tokens.

### Try it

There is **no emulator for sending push**. The Emulator Suite does not include FCM, so this lab uses the real service. FCM is free, including on the Spark plan.

First, create a small web project and add Firebase:

```bash
npm create vite@latest push-lab
cd push-lab
npm install firebase
```

Next, create `public/firebase-messaging-sw.js`. Replace `VER` with the firebase version in your `package.json`:

```js
importScripts("https://www" +
 ".gstatic.com/firebasejs/" +
 "VER/firebase-app-compat.js");
importScripts("https://www" +
 ".gstatic.com/firebasejs/" +
 "VER/firebase-messaging-" +
 "compat.js");
firebase.initializeApp({
  /* same config as main.js */
});
firebase.messaging();
```

Then:

1. In `main.js`, initialise your `notes-demo` app with its config and add a button that runs `askPush`. After permission is granted, call the older `getToken(messaging, { vapidKey })` and print the result with `console.log`. This throwaway page uses `getToken` because the console's test box asks for a registration token. Your real app uses `register()`.
2. Run `npx vite`, open the local address it prints, click the button, allow notifications, and copy the token from the browser console.
3. In the Firebase console, open Messaging (under DevOps & Engagement), then New campaign, then Notifications. Type a title and text, click Send test message, paste the token into "Add an FCM registration token", and click Test.
4. The console tab has focus, so your lab page is in the background: you should see a system notification. Now add the `onMessage` code to `main.js`, open the lab page in its own window with focus, and send again from the console in a second window. No alert appears, but your handler runs.

### Common mistakes

- **Service worker in the wrong place.** You see a registration error mentioning `firebase-messaging-sw.js`. Fix: put the file at the site root so it is served at `/firebase-messaging-sw.js`.
- **One token per user.** Only the newest device gets reminders. Fix: store many tokens under `users/{uid}/tokens`, one document each.
- **Asking for permission on page load.** Most users click Block and you can never ask again. Fix: ask when the user sets their first reminder.
- **Registration fails with a permission error.** With newer versions of the SDK, the FCM Registration API must be switched on for your project. Fix: open your project in the Google Cloud console, find the FCM Registration API, and enable it.
- **Not deleting the token on sign-out.** The next person on that device receives someone else's alerts. Fix: delete the token document before `signOut`.
