## 2. Project & plans

After this skill you will have a Firebase project, a web app connected to it, the command-line tool installed, and a full copy of Firebase running on your own computer. You will also know what the free plan covers and when you must add billing.

### Create the project

A **Firebase project** is the container for one app: its users, data, files and settings. One project can hold several apps, for example the web, Android and iOS versions of the Notes app. They all share the same users and data.

Steps:

1. Open the **Firebase console** (the website where you manage projects; go to firebase.google.com and choose "Go to console"). Sign in with a Google account.
2. Click **Create a project**.
3. Type a name, such as `notes-demo`.
4. Look at the **project ID** shown under the name. It is used in web addresses and commands, and must be unique across all of Firebase, so it may get extra characters, like `notes-demo-4f2a1`. You can edit it now. **You can never change it later.**
5. The wizard may offer optional extras, such as Google Analytics or AI assistance. You can turn Analytics off for now and add it later (see Measure & protect).
6. Click **Create project** and wait a few seconds.

In this course we write the project ID as `notes-demo`. Use your own real ID wherever you see it.

Good habit: create **two projects**, one for testing and one for real users, such as `notes-demo-dev` and `notes-demo`. A mistake in testing then cannot touch real data.

### Register a web app and read the config

A project does nothing until an app is registered with it.

1. On the project overview page, click the **Web** icon (it looks like `</>`).
2. Enter a nickname, such as "Notes web". Only you see it.
3. Leave Hosting unticked for now. Click **Register app**.

Firebase now shows a **config object**: a small set of values that tells the SDK which project to talk to. It looks like this:

```js
const firebaseConfig = {
  apiKey: "YOUR_API_KEY",
  authDomain:
    "notes-demo.firebaseapp.com",
  projectId: "notes-demo",
  storageBucket:
    "notes-demo.firebasestorage.app",
  messagingSenderId: "YOUR_ID",
  appId: "YOUR_APP_ID",
};
```

Find it again under **Project settings → General**.

#### Why the config is not a secret

An **API key** is a string an app sends with its requests so the service knows which project they belong to. Some API keys work like passwords and must stay secret. The **web apiKey** in this config is not one of them.

The word `apiKey` sounds secret, but it is not. Every user's browser downloads it with your app, so anyone can read it. The Firebase docs say these keys are fine to include in your code. It only identifies your project. It does not grant access to data.

What protects your data is **security rules** (see Security rules) and **App Check** (see Measure & protect). If your rules are open, hiding the key will not save you.

Some things **are** secret and must never be in app code: a **service account key** (a JSON file that gives full admin power over the project), and keys for paid AI APIs. Keep those on a server only.

### Install and initialise the SDK

The **SDK** is the library your app uses to call Firebase. For the web, install it with **npm** (the package manager that comes with Node.js):

```bash
npm install firebase
```

Then create one file that starts Firebase. Every other file imports from it.

```js
// firebase.js
import { initializeApp }
  from "firebase/app";
import { getAuth }
  from "firebase/auth";
import { getFirestore }
  from "firebase/firestore";

const firebaseConfig = {
  // paste your config here
};

export const app =
  initializeApp(firebaseConfig);
export const auth = getAuth(app);
export const db = getFirestore(app);
```

This is the **modular SDK**: you import only the functions you use, so your app downloads less code. Each product has its own path, such as `firebase/auth` or `firebase/storage`. Call `initializeApp` once, in this one file, and import `app`, `auth` and `db` everywhere else.

For Android and iOS, the console gives you a config file instead (`google-services.json` or `GoogleService-Info.plist`) to add to the app project.

### The CLI and firebase init

The **CLI** (command-line interface) lets you set up, test and deploy from your terminal. Its package is called `firebase-tools`. You need Node.js 20 or later.

```bash
npm install -g firebase-tools
firebase --version
firebase login
```

`firebase login` opens a browser so you can approve access with your Google account. Then:

```bash
firebase projects:list
```

This lists the projects you can use. You should see `notes-demo`.

Now go to your app folder and run:

```bash
firebase init
```

`init` asks which products to set up (Firestore, Hosting, Functions, Emulators and more) and which project to use. It may ask extra optional questions; answer No if you are not sure. It writes two files:

| File | What it holds |
|---|---|
| `firebase.json` | Which products, ports, folders |
| `.firebaserc` | Your project aliases |

Commit both to your code repository. They contain no secrets. To switch the active project, run `firebase use notes-demo-dev`.

### The Emulator Suite

The **Emulator Suite** runs local copies of Firebase products (Auth, Firestore, Functions, Storage, Hosting and others) on your computer. It is free, works offline, and cannot touch real data or bills. Use it for daily work and for every lab in this course.

It needs **Java** (JDK 21 or later) as well as Node.js, because some emulators are Java programs.

Start it with:

```bash
firebase emulators:start
```

Then point your app at them. Add this to `firebase.js`, after creating `auth` and `db`:

```js
import { connectAuthEmulator }
  from "firebase/auth";
import { connectFirestoreEmulator }
  from "firebase/firestore";

// only on your own computer
if (location.hostname ===
    "localhost") {
  connectAuthEmulator(auth,
    "http://127.0.0.1:9099");
  connectFirestoreEmulator(db,
    "127.0.0.1", 8080);
}
```

The default ports are 9099 for Auth, 8080 for Firestore, 9199 for Storage, 5001 for Functions, 5000 for Hosting and 4000 for the **Emulator UI** (a web page to see and edit local data).

Tip: a project ID that starts with `demo-`, such as `demo-notes`, is a **demo project**. It has no real project behind it, so code can only reach emulators. It is the safest choice for learning.

### Spark, Blaze and regions

Firebase has two **pricing plans**.

| | Spark | Blaze |
|---|---|---|
| Cost | Free | Pay for what you use |
| Card needed | No | Yes |
| Free quota | Yes | Yes, the same |

**Spark** is free. It includes Authentication (email and Google sign-in), Firestore, Hosting and Cloud Messaging, each with a free quota. If you pass a quota, that product stops working for your project until the quota resets. You are never charged.

**Blaze** is pay-as-you-go. You link a **Cloud Billing account** (a Google payment account with a card). You keep the same free quotas and pay only above them. On Blaze, Cloud Functions may still have small costs, even at low use, because they build and store your code with other Google Cloud services.

Products that need **Blaze**, at the time of writing: Cloud Functions, Cloud Storage (including the default bucket for photos), App Hosting and phone-number sign-in. So the Notes app can start on Spark, but needs Blaze for photos and reminders. The emulators run all of them free.

**Billing basics.** A **budget alert** only sends you an email. It does **not** stop spending. Set one on day one anyway. For current prices and quotas, see the Firebase pricing page; numbers change. See Costs & safety for details.

#### Picking a region

A **location** (or region) is where Google stores your data. Each product picks its own: you choose Firestore's location when you create the database, and **it cannot be changed later**. Cloud Functions default to `us-central1` unless you set one. Choose a location close to most of your users, and in the same place for Firestore, Storage and Functions, so requests do not travel far.

### Try it

You will run Firebase on your computer, with no project and no card. About 10 minutes.

1. Check your tools:

```bash
node -v
java -version
```

You should see Node `v20` or higher and Java `21` or higher. If not, install them first.

2. Install the CLI and sign in:

```bash
npm install -g firebase-tools
firebase login
```

You should see `Success! Logged in as` and your email.

3. Make a folder and set up emulators:

```bash
mkdir notes-lab
cd notes-lab
firebase init emulators
```

When asked for a project, choose **Don't set up a default project**. Select **Authentication** and **Firestore** emulators. Accept the default ports. Say Yes to the Emulator UI and to downloading now.

4. Start them with a demo project ID:

```bash
firebase emulators:start \
  --project demo-notes
```

You should see a table with Authentication at `127.0.0.1:9099` and Firestore at `127.0.0.1:8080`, then a line like:

```text
All emulators ready! It is now
safe to connect your app.
View Emulator UI at
http://127.0.0.1:4000/
```

5. Open `http://127.0.0.1:4000/` in your browser. Go to **Firestore**, click **Start collection**, name it `notes`, and add a document with a field `text` set to `First note`. Go to **Authentication** and add a user with any email.

6. Press `Ctrl+C` in the terminal. The emulators stop, and the data is gone. Emulator data is temporary unless you export it.

### Common mistakes

1. **Using a real project for experiments.** You will see: test notes mixed with real users' data. Fix: use a `demo-` project with the emulators, or a separate `-dev` project.
2. **Java too old or missing.** You will see: `emulators:start` stops with an error about Java. Fix: install JDK 21 or later and check with `java -version`.
3. **Hiding the config but leaving rules open.** You will see: data still readable by anyone. Fix: the config is public by design; write and test security rules.
4. **Forgetting to connect to the emulators.** You will see: your local app writes to the real project, or fails with a permission error. Fix: call `connectAuthEmulator` and `connectFirestoreEmulator` before any read or write.
5. **Choosing a location without thinking.** You will see: slow requests for users far away, and no way to move the database. Fix: pick the location close to your users before creating Firestore.
