## 12. Final project

In this skill you build the complete Notes app from an empty folder to a public launch. Each step says what to do, how to check that it works, and which earlier skill to revisit if it fails. A final review and self-test close the course.

### Steps 1 to 4: the base

Do the steps in order. Each one rests on the one before it. Work in the Emulator Suite until step 6.

**1. Project and emulator.** Create the project `notes-demo` and register a web app. Run `firebase init` and choose Firestore, Functions, Hosting, Storage and Emulators. Then run `firebase emulators:start`.
- Verify: the Emulator UI opens at `localhost:4000` and lists each emulator as running.
- If it fails: revisit Project & plans.

**2. Sign-in.** Add email/password and Google sign-in. Connect the app to the Auth emulator. Log the uid in `onAuthStateChanged`.
- Verify: after sign-in, the user appears in the Auth tab of the Emulator UI, and the same uid shows in your log after a page reload.
- If it fails: revisit Sign-in (Auth).

**3. Firestore model.** Write each note to `notes` with `ownerId`, `text`, `createdAt` and `photoPath`. Add `remindAt` and `reminded` too, which the reminder in Sending push uses. Show the list with a live listener filtered by `ownerId` and limited to 50.
- Verify: a new note appears in the list without a reload, and in the Firestore tab with your uid as `ownerId`.
- If it fails: revisit Firestore data. A "needs an index" error gives a link to create it.

**4. Rules and their tests.** Write rules so that a user can read and write only notes where `ownerId` equals their uid, and only their own `users/{uid}` data. Then write tests.
- Verify: `firebase emulators:exec "npm test"` passes, including a test where one user fails to read another user's note.
- If it fails: revisit Security rules.

The key test looks like this:

```js
// Bob tries to read Alice's note
const bob = env
  .authenticatedContext("bob")
  .firestore();
await assertFails(
  getDoc(doc(bob, "notes/n1"))
);
// Alice reads her own note
const alice = env
  .authenticatedContext("alice")
  .firestore();
await assertSucceeds(
  getDoc(doc(alice, "notes/n1"))
);
```

Here `env` comes from `initializeTestEnvironment` in `@firebase/rules-unit-testing`, and note `n1` was seeded with `ownerId: "alice"`.

### Steps 5 to 7: photos, push, hosting

**5. Photo upload.** Upload to `photos/{uid}/{noteId}.jpg` and save that path in `photoPath`. Write Storage rules: only the owner may write, only images, with a size limit. Cloud Storage for Firebase needs the Blaze plan in a real project; the emulator is free.
- Verify: the photo appears in the Storage tab; an upload to another user's folder is denied; a large file is denied.
- If it fails: revisit Functions & Hosting (the Cloud Storage part).

**6. A reminder push.** Save each device's token under `users/{uid}/tokens`. Then write a scheduled function that sends a daily reminder. Scheduled functions need Blaze. Push itself has no emulator, so test the send with a real device.

```js
import { onSchedule } from
  "firebase-functions/v2/scheduler";
import { initializeApp } from
  "firebase-admin/app";
import { getFirestore } from
  "firebase-admin/firestore";
import { getMessaging } from
  "firebase-admin/messaging";

initializeApp();
```

```js
export const dailyReminder =
 onSchedule("every day 09:00",
 async () => {
  const snap = await getFirestore()
    .collectionGroup("tokens").get();
  // Doc id = the push address
  const fids = snap.docs
    .map((d) => d.id);
  if (fids.length === 0) return;
  // Max 500 per call
  const res = await getMessaging()
    .sendEachForMulticast({ fids,
      notification: { title: "Notes",
        body: "Review your notes" }
    });
  console.log(res.failureCount);
 });
```

- This demo reminds every device once a day. Sending push shows the version that reminds one note's owner at the time they chose.
- Verify: deploy with `firebase deploy --only functions`, run the job once with "Force run" on the Cloud Scheduler page of the Google Cloud console, and see the notification on your phone. The log shows the failure count.
- If it fails: revisit Push basics for tokens and permission, and Sending push for errors and removing stale tokens.

**7. Hosting.** Build the web app and run `firebase deploy --only hosting`.
- Verify: the app loads at `notes-demo.web.app`, and sign-in works there. If sign-in fails on a custom domain, add it to the authorised domains in Auth settings.
- If it fails: revisit Functions & Hosting.

### Steps 8 to 10: protect and launch

**8. App Check and monitoring.** Add App Check with the reCAPTCHA Enterprise provider for web and a debug provider for local work. Watch the App Check metrics for a few days, then turn on enforcement for Firestore, Storage and Functions. Add Analytics and Performance Monitoring; add Crashlytics in Android or iOS builds.
- Verify: the App Check page shows most requests as verified before you enforce. After you enforce, a plain script that calls Firestore with your config is refused.
- If it fails: revisit Measure & protect.

**9. Budget alert.** Set a budget with email alerts in the Google Cloud console billing pages, at low amounts such as half and all of what you expect to spend. Do this the moment you move to Blaze, which may be step 5.
- Verify: the budget lists your project and the alert thresholds.
- Remember: a budget alert warns you; it does not stop spending.
- If it fails: revisit Costs & safety.

**10. Launch checklist.** Walk the final review below. Fix every "no" before you share the link.
- Verify: a friend on another device can sign up, write a note, add a photo and get the next reminder, and cannot see your notes.
- If it fails: find the failing part and go back to its step.

### Try it

This is the build-it checklist. Tick each line only after its "Verify" step passed.

- Emulators start and the UI opens
- Sign-in works and the uid survives a reload
- Notes are saved with `ownerId` and update live
- Rules tests pass, including the "other user" test
- Photos upload; wrong folder and big files are denied
- Tokens are saved; the reminder arrives on a phone
- The app works at `notes-demo.web.app`
- App Check is enforced after watching metrics
- A budget with alerts exists
- The final review has no open "no"

Plan about one short session per step. Steps 1 to 4 cost nothing. Steps 5 and 6 need Blaze for the real project, but you can build and test most of each in the emulator first.

### Final review checklist

**Security**
- No rule allows `read, write: if true`, and no test-mode rules remain.
- Every rule that touches `notes` checks `request.auth.uid` against `ownerId`.
- No service-account key is in the app, in the repository or in a public place.
- App Check is enforced.

**Cost**
- Every list query has a limit.
- No screen reads a whole collection.
- Functions cannot trigger themselves in a loop.
- A budget alert exists and goes to an inbox someone reads.

**Privacy**
- A privacy policy says what you collect, including Analytics.
- A user can delete their account, and this also deletes their notes, photos and tokens.
- The Firestore location suits your users and any residency rules.

**Reliability**
- Stale tokens are removed after send errors.
- Firestore backups or point-in-time recovery are turned on.
- Rules and indexes are in files and deployed with the CLI, not edited by hand in the console.

### Common mistakes

- **Skipping the rules tests.** What you see: the app works, but any signed-in user can read every note. Fix: write the "other user" test in step 4 and keep it passing.
- **Building against the live project.** What you see: test data and test users mixed with real ones, and reads on your bill. Fix: stay in the emulator until step 6.
- **Enforcing App Check on day one.** What you see: real users are refused because their app was not yet sending tokens. Fix: watch the metrics first, then enforce.
- **Setting the budget after the bill.** What you see: a surprise charge from a loop or a busy screen. Fix: set the budget the same day you move to Blaze.
- **Forgetting account deletion.** What you see: deleted users' photos and tokens stay forever. Fix: delete `notes`, `photos/{uid}/` and `users/{uid}` together, for example in a function.
