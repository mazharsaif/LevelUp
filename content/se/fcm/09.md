## 9. Measure & protect

After this skill you can see what people do in the Notes app, find out when it breaks or feels slow, change its behaviour without shipping a new version, and block requests that do not come from your real app. You will also know which of these tools to add first.

### Five questions after launch

Once real people use your app, five questions come up again and again. Firebase has one tool for each.

| Question | Tool |
|---|---|
| What do people do? | Analytics |
| Where does it break? | Crashlytics |
| Where is it slow? | Performance |
| Can I change it safely? | Remote Config |
| Is this request from my app? | App Check |

Each tool is a separate part of the SDK that you import only if you use it. Every tool has a cost: more code, more data about your users, more screens to check. Add a tool when you have its question, not before.

The **Emulator Suite** (local copies of Firebase services, see Project & plans) does not include any of these five tools, so most need a real project. The lab shows what you can still try locally.

### Analytics: events and user properties

**Google Analytics for Firebase** records **events** (named things that happen, such as "note created") and **user properties** (facts about a user that change slowly, such as the theme they chose). Some events, such as first visits and page views, are recorded automatically. You add custom events for the actions that matter to your app.

```js
import {
  getAnalytics, isSupported,
  logEvent, setUserProperties
} from "firebase/analytics";
import { app } from "./firebase.js";

let analytics = null;
// Not every browser supports it
isSupported().then((ok) => {
  if (ok) {
    analytics = getAnalytics(app);
  }
});

export function trackNote(note) {
  if (!analytics) return;
  logEvent(analytics, "note_created",
    { has_photo: note.photoPath
        ? "yes" : "no" });
}
```

Later you can call `setUserProperties(analytics, { theme: "dark" })` to compare dark-theme users with others.

Rules that keep the data useful and legal:

- Use short names with letters, numbers and underscores: `note_created`, not `Note Created!`.
- Never send personal data: no note text, no email, no uid in event parameters. Send categories such as `"yes"` or `"long"`.
- Log a few events that answer real questions ("Do people who add photos come back?"), not every click.
- Ask for consent where your users' law requires it.

Events are sent in batches, so reports lag. If you like SQL, you can link the project to **BigQuery** (Google's data warehouse) and get raw events as tables you can query. Check the docs for the plan and cost details of the export.

### Crashlytics and Performance Monitoring

**Crashlytics** records crashes and other errors from real devices: the stack trace (the list of functions that were running), the device, the OS and the app version. You can also record **non-fatal errors** (caught errors you still want to know about), add log lines, and attach custom keys such as the current screen.

The most useful part is **grouping**. Crashlytics puts events with the same failure point into one **issue** and shows how many users it hits. A thousand crash reports become "three issues, and one of them hits 80% of affected users". You fix that one first.

Crashlytics is strongest on Android, iOS, Flutter and Unity. A web version exists as a **preview** (an early release that may change without warning) and needs the Blaze plan. For a web-only Notes app it is optional at first.

**Performance Monitoring** measures speed. On the web it records page load times, Core Web Vitals (standard measures of how fast a page feels) and network requests, with no extra code. You can also time your own code with a **custom trace**:

```js
import {
  getPerformance, trace
} from "firebase/performance";

const perf = getPerformance(app);

async function saveNote(note) {
  const t = trace(perf, "save_note");
  t.start();
  await addNoteToFirestore(note);
  t.stop(); // the time is recorded
}
```

The web SDK is marked beta in the docs. Look at the slowest users (the 90th percentile), not the average: an average can look fine while one user in ten waits a long time.

### Remote Config: change the app without a release

**Remote Config** stores values on Firebase servers that your app reads at start-up. You change a value in the console, and apps pick it up the next time they fetch. No new release is needed.

You always set **defaults** in the code. The app uses them until a fetch succeeds, and also when it is offline.

```js
import {
  getRemoteConfig, getBoolean,
  fetchAndActivate
} from "firebase/remote-config";

const rc = getRemoteConfig(app);
rc.defaultConfig = {
  photos_enabled: true,
  max_note_length: 2000
};

// Fetch, then use the new values
await fetchAndActivate(rc)
  .catch(() => {}); // keep defaults

const photosOn =
  getBoolean(rc, "photos_enabled");
if (photosOn) showPhotoButton();
```

`fetchAndActivate` does two things: it downloads new values and makes them active. Fetches are throttled. The default minimum time between fetches is 12 hours. Lower it only while developing.

A **feature flag** is a value like `photos_enabled` that turns a feature on or off. If photo uploads start failing, you set it to `false` and the button disappears for everyone on their next fetch.

To release slowly, use a **rollout**: show the new value to a small percentage of users, watch crashes and key events, then raise the percentage. If things go wrong, roll back.

**A/B Testing** builds on this. It gives different values to random groups of users and uses Analytics events to measure which value works better, for example two wordings of the reminder prompt. It needs many users to give a clear answer.

Two rules. Values are visible to anyone who inspects the app, so never store secrets there, and never use a flag as security: rules still decide who may read what. Keep flags few, and delete each one from the code and the console once its feature is fully on.

### App Check: is this request from your app?

Your web config is public. Anyone can copy it and call your Firestore from a script. Rules stop it reading other people's notes, but it can still sign up and flood you with writes you pay for.

**App Check** proves that a request comes from your genuine app, running on a genuine device or browser. It does not prove who the user is (that is Auth), or what they may do (that is security rules). It adds a third check.

Each platform has an **attestation provider** (a service that vouches for the app):

| Platform | Provider |
|---|---|
| Android | Play Integrity |
| Apple | App Attest, DeviceCheck |
| Web | reCAPTCHA Enterprise |

reCAPTCHA v3 is also still supported on the web, but the docs recommend Enterprise for new apps.

```js
import {
  initializeAppCheck,
  ReCaptchaEnterpriseProvider
} from "firebase/app-check";

initializeAppCheck(app, {
  provider:
    new ReCaptchaEnterpriseProvider(
      "YOUR_SITE_KEY"),
  isTokenAutoRefreshEnabled: true
});
```

App Check can protect Firestore, Realtime Database, Cloud Storage, callable functions and more. Turn it on gradually:

1. Add the SDK and release the app.
2. Watch the App Check request metrics in the console for a while. You see how many requests are verified.
3. When nearly all real traffic is verified, turn on **enforcement** (rejecting unverified requests) one product at a time. It can take up to 15 minutes to apply.

For local work and tests, use the **debug provider**, so the emulator and test runs are not blocked. App Check reduces abuse; it does not remove all of it.

### Which tool to add first

| Your problem | Add first |
|---|---|
| Users leave, you do not know why | Analytics |
| Mobile app crashes | Crashlytics |
| App feels slow | Performance |
| Risky new feature | Remote Config |
| Scripts hit your database | App Check |
| Two designs, which is better? | A/B Testing |

For a new Notes app, a sound order is: App Check (abuse costs money from day one), then Analytics with three or four events, then Remote Config with one kill switch for photo uploads.

### Try it

Part A runs locally with no project. Part B needs a free Firebase project.

**Part A: Remote Config defaults (5 minutes).**

```bash
mkdir rc-lab && cd rc-lab
npm init -y
npm install firebase vite
```

Create `index.html`:

```html
<script type="module"
  src="main.js"></script>
```

Create `main.js`:

```js
import { initializeApp }
  from "firebase/app";
import {
  getRemoteConfig, getValue,
  fetchAndActivate
} from "firebase/remote-config";

const app = initializeApp({
  apiKey: "YOUR_API_KEY",
  projectId: "notes-demo",
  appId: "YOUR_APP_ID"
});
const rc = getRemoteConfig(app);
rc.defaultConfig =
  { photos_enabled: true };

const v = getValue(rc,
  "photos_enabled");
console.log(v.asBoolean(),
  v.getSource());
fetchAndActivate(rc).catch((e) =>
  console.log("failed", e.code));
```

Run `npx vite` and open the address it prints. In the browser console you should see `true default`, then a "failed" line, because the key is fake. The app still has its value, exactly as a real app does offline.

**Part B: an Analytics event (5 minutes).** In a free project with Analytics turned on, put your real config in the file. Call `logEvent(getAnalytics(app), "note_created")`. Install the Google Analytics Debugger extension for Chrome, turn it on, reload, and open Analytics → DebugView in the console. Your event should appear within a minute or two.

### Common mistakes

1. **Personal data in events.** You send note text or emails as parameters. You break Analytics policy and possibly privacy law. Fix: send categories only.
2. **Enforcing App Check on day one.** Real users get permission errors because older versions send no token. Fix: monitor the metrics first, then enforce one product at a time.
3. **A low fetch interval in production.** Fetches fail with throttling errors. Fix: use a low interval only in development builds.
4. **Secrets or security in Remote Config.** Anyone can read the values. Fix: keep secrets on a server, and enforce access with security rules.
5. **Flags that never die.** The code fills with branches nobody tests. Fix: remove each flag once its rollout reaches 100%.

### Check yourself

1. Your Notes app gets a burst of new accounts that each write thousands of notes from a script. Rules are correct. Which tool helps, and how do you turn it on safely?
2. Why is grouping crashes into issues more useful than a list of reports?
3. Photo uploads start failing in production. What could you change in seconds, and what must already be in the code?
4. Which of these needs a real project, not the Emulator Suite: Firestore, Remote Config, Analytics?

**Answers.** 1. App Check: ship the SDK, watch the verified-request metrics, then enforce product by product. 2. It shows which few problems hit the most users, so you fix the biggest first. 3. Set the `photos_enabled` flag to false in Remote Config; the app must already read the flag and have a default. 4. Remote Config and Analytics; Firestore runs in the emulator.
