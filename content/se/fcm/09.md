## 9. Firestore data

This skill covers Cloud Firestore: how data is shaped, how to model it without joins, and how its billing works.

### Documents and collections

Firestore is a managed **document database**. Data lives in **documents** (a bag of fields, up to about 1 MiB) grouped into **collections**, and documents can hold sub-collections. [consensus; 1 MiB checked 2026-11-23]

Two selling points:
- **Real-time listeners**: the app is notified when data changes.
- **Offline support**: mobile and web SDKs cache locally and sync later.

It is **not** a relational database. There are no joins, and every query runs on an index. Queries on several fields need a composite index you define. Firestore also now comes in more than one **edition** with different limits, including a MongoDB-compatible option [fast-moving, unsure of details], so read the current edition docs before you plan.

### No joins: model for the query

Decide the screens first, then shape the documents to serve them. For "my last 20 orders with the product name", you copy the product name and the price paid *into the order document*. That is also correct, because an order should keep the price at purchase time.

```python
# needs initialize_app() and a project (or the emulator)
from firebase_admin import firestore

db = firestore.client()

def last_orders(uid: str, n: int = 20) -> list[dict]:
    q = (db.collection("orders")
           .where("uid", "==", uid)                                    # filter on one field ...
           .order_by("created", direction=firestore.Query.DESCENDING)  # ... sort on another: needs a composite index
           .limit(n))                                                  # always cap what you read
    return [d.to_dict() for d in q.stream()]                           # n documents = n billed reads
```

The first run without its composite index fails with an error that links to creating it. The cost of denormalising is on the write side: renaming a product means updating every copy you decided to keep.

### What it costs

Firestore charges per document read, write and delete, plus storage and network. The standard free quota allowed 50,000 reads, 20,000 writes and 20,000 deletes per day. [checked 2026-11-23, fast-moving]

The lesson: **a screen that loads a 500-document query costs 500 reads every time.** A bug that loops costs money fast. Estimate before you build.

```python
def monthly_reads(users: int, opens_per_day: int, docs_per_open: int, days: int = 30) -> int:
    return users * opens_per_day * docs_per_open * days

reads = monthly_reads(users=2_000, opens_per_day=4, docs_per_open=100)
price_per_100k = 0.06  # PLACEHOLDER: look up the current price for your region
print(f"{reads:,} reads/month, about ${reads / 100_000 * price_per_100k:,.2f} at ${price_per_100k}/100k")
```

The price is a placeholder, not a quote. The shape of the maths (users times opens times documents) is what carries over.

### Limits that shape design

- Documents are about 1 MiB. Large blobs belong in Cloud Storage.
- There is no join, and there are index limits.
- Sustained writes to a single document are rate-limited, so a global counter needs sharding. [unsure of the current figure, check the scale docs]
- Always `limit`, paginate, and avoid listeners on huge collections.
