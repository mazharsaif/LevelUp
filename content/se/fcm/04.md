## 4. Firestore data

After this skill you can save, read, change and delete notes in Cloud Firestore, ask for "my last 20 notes", and see changes live. You will also know how to shape data without joins, and how to estimate what it costs before you build.

### Documents and collections

**Cloud Firestore** is the Firebase database. It is a **document database**: it stores small records called documents, not rows in tables.

- A **document** is one record with named fields, like a small JSON object. It has an id, unique inside its collection.
- A **collection** is a folder of documents. It has no fixed shape: two documents in it may have different fields.
- A **subcollection** is a collection inside a document.

The Notes app uses these paths:

```text
notes/{noteId}
  ownerId, text,
  createdAt, photoPath
users/{uid}
  name, ...
users/{uid}/tokens/{tokenId}
```

A path always goes collection, document, collection, document. Reading a document does not read its subcollections; each read is separate and you pay for what you read.

There are no joins and no SQL. You get fast reads of documents and simple queries. In return, you plan your data around the screens you will show. Firestore fits apps with many users each reading small sets of data. It fits badly for reports across all data ("average note length per country"), for full-text search, and for data with many links between tables. For those, export to an analysis tool or use a relational database.

### Create, read, update, delete

```js
import {
  getFirestore, collection, doc,
  addDoc, getDoc, updateDoc,
  deleteDoc, serverTimestamp,
} from "firebase/firestore";

const db = getFirestore(app);
const uid = auth.currentUser.uid;

// Create: Firestore picks the id
const ref = await addDoc(
  collection(db, "notes"), {
    ownerId: uid,
    text: "Buy milk",
    createdAt: serverTimestamp(),
    photoPath: null,
  });
```

`serverTimestamp()` asks the server to fill in its own time, so a wrong phone clock does not matter.

```js
// Read one note by id
const snap = await getDoc(
  doc(db, "notes", ref.id));
if (snap.exists()) {
  console.log(snap.data().text);
}
// Change only these fields
await updateDoc(ref, {
  text: "Buy oat milk" });
// Delete the note
await deleteDoc(ref);
```

When you know the id yourself, use `setDoc`. The profile lives at the user's uid:

```js
import { setDoc }
  from "firebase/firestore";
await setDoc(doc(db, "users", uid),
  { name: "Ana" }, { merge: true });
```

Without `{ merge: true }`, `setDoc` replaces the whole document and drops any field you did not send. Deleting a document does not delete its subcollections; you must delete those separately.

### Queries and live listeners

A **query** asks for the documents in one collection that match conditions:

```js
import {
  query, where, orderBy, limit,
  getDocs, onSnapshot,
} from "firebase/firestore";

const q = query(
  collection(db, "notes"),
  where("ownerId", "==", uid),
  orderBy("createdAt", "desc"),
  limit(20));

const res = await getDocs(q);
res.forEach((d) =>
  console.log(d.id, d.data().text));
```

Always add `limit`. Without it, a query returns every match, and you pay for each one.

`getDocs` reads once. A **live listener** keeps the result up to date: Firestore sends changes as they happen, so a note written on the laptop appears on the phone.

```js
const stop = onSnapshot(q, (s) => {
  s.docChanges().forEach((c) => {
    // added, modified or removed
    console.log(c.type, c.doc.id);
  });
});
// On sign-out or leaving the screen
stop();
```

To show the next 20 notes, use a **cursor**: start after the last document you already have.

```js
import { startAfter }
  from "firebase/firestore";
const last =
  res.docs[res.docs.length - 1];
const page2 = query(
  collection(db, "notes"),
  where("ownerId", "==", uid),
  orderBy("createdAt", "desc"),
  startAfter(last),
  limit(20));
```

Do not use `offset` to skip pages. Firestore still reads the skipped documents, and you pay for them.

### Indexes

An **index** is a sorted list that lets Firestore find matches without scanning everything. Every query needs one.

- **Single-field indexes** are made for you, for every field. They cover queries on one field, such as `where("ownerId", "==", uid)`.
- **Composite indexes** cover several fields at once, such as `ownerId` plus `orderBy("createdAt")`. You create these yourself.

When a query needs a composite index that does not exist, it fails with an error saying the query requires an index. The message contains a link. Open it, and the console fills in the index for you; it is ready after a few minutes. For a project you keep in code, add the index to `firestore.indexes.json` and run `firebase deploy --only firestore:indexes`.

Indexes are not free. Each index entry uses storage, and every write must update every index the document is in. You can switch off indexing for a field you never query, such as a long `text` field. This saves storage and avoids one limit: a field whose value always grows, like a timestamp, limits fast writes to the whole collection when it is indexed (the Firestore best practices page gives the number).

### Modelling without joins

Imagine a shared board in the Notes app: "show the last 20 notes, each with the author's name". In SQL you would join notes with users. Firestore has no joins. You have two choices.

**Option A, read the users too.** Query 20 notes, then `getDoc` each `users/{ownerId}`. That is up to 20 extra reads every time the board opens, and a slower screen.

**Option B, copy the name on purpose.** Store `authorName` inside each note when you write it:

```js
await addDoc(
  collection(db, "notes"), {
    ownerId: uid,
    authorName: "Ana",
    text: "Team lunch at 1",
    createdAt: serverTimestamp(),
    photoPath: null,
  });
```

Now the board is one query and 20 reads. Copying data on purpose to make reads cheap is called **denormalisation**. Its cost: when Ana changes her name, every one of her notes holds the old one. If she has 300 notes, fixing them is 300 writes, usually done in a Cloud Function (see Functions & Hosting).

The rule: copy data that is read often and changes rarely. A name fits. A value that changes every minute, such as "online now", does not; read that from its own document.

### Billing, offline use and limits

Firestore charges mainly per **document read**, **document write** and **document delete**, plus stored data and network traffic. There is a free daily quota. Reads usually dominate.

- A query costs one read per document returned, and at least one read even if nothing matches.
- A listener costs one read per document in the first result, then one read each time a document is added to the result, changed, or leaves it.
- A listener that reconnects after more than 30 minutes offline is billed as a new query.

A worked estimate, with **R** as a placeholder price per 100,000 reads (look up the real one on the pricing page):

| Action | Reads per day |
|---|---|
| 1,000 users open 5 times x 20 | 100,000 |
| Same, no limit, 500 notes | 2,500,000 |

The limit alone changes the bill from 1 x R to 25 x R per day. A listener on a big query is expensive because every change reaches every open screen: 500 people watching a board, 200 new notes a day, is another 100,000 reads.

**Offline persistence** keeps a local copy of data on the device. Reads work without a network, and writes wait in a queue and are sent later. It is on by default on Android and iOS, and off by default on the web. Turn it on for the web when you create Firestore:

```js
import {
  initializeFirestore,
  persistentLocalCache,
} from "firebase/firestore";
const db = initializeFirestore(app, {
  localCache: persistentLocalCache(),
});
```

Main limits: a document can be at most 1 MiB, and maps and arrays can nest at most 20 levels deep. One document cannot take a high write rate, so do not keep a single global counter document. Store a photo in Cloud Storage and keep only its `photoPath` in the note.

### Try it

You will write and query notes in the **Firestore emulator**, a free local copy of Firestore. Use the project folder from Project & plans, with the Auth and Firestore emulators set up. For this lab only, make `firestore.rules` say "any signed-in user may read and write"; Security rules shows how to write real ones:

```text
rules_version = '2';
service cloud.firestore {
  match /databases/{d}/documents {
    match /{doc=**} {
      allow read, write:
        if request.auth != null;
    }
  }
}
```

1. Run `firebase emulators:start --only auth,firestore`
2. In the lab folder from Sign-in (Auth), save `notes.mjs`:

```js
import { initializeApp }
  from "firebase/app";
import * as A from "firebase/auth";
import * as F
  from "firebase/firestore";

const app = initializeApp({
  apiKey: "demo-key",
  projectId: "notes-demo" });
const auth = A.getAuth(app);
A.connectAuthEmulator(auth,
  "http://127.0.0.1:9099");
const db = F.getFirestore(app);
F.connectFirestoreEmulator(db,
  "127.0.0.1", 8080);
```

3. Add this below it:

```js
const u = await A
  .signInAnonymously(auth);
const uid = u.user.uid;
const col = F.collection(db, "notes");
for (const t of ["a", "b", "c"]) {
  await F.addDoc(col, { ownerId: uid,
    text: t,
    createdAt: F.serverTimestamp() });
}
const q = F.query(col,
  F.where("ownerId", "==", uid),
  F.orderBy("createdAt", "desc"),
  F.limit(2));
const r = await F.getDocs(q);
r.forEach((d) =>
  console.log(d.data().text));
process.exit(0);
```

4. Run `node notes.mjs`. You should see `c` then `b`: newest first, only two.
5. Open `http://127.0.0.1:4000/firestore` and see the three notes.

The emulator runs this query without a composite index. It does not check for indexes, so a query that works on your computer can still fail in production with a "requires an index" error. When that happens, the error includes a link to create the index. Create it before you launch.

### Common mistakes

1. **No `limit` on a list query.** Bills grow with data. Fix: always limit, and page with cursors.
2. **`setDoc` without merge.** Fields vanish from the profile. Fix: use `updateDoc` or `{ merge: true }`.
3. **Ignoring the index error.** The screen stays empty in production. Fix: open the link in the error, or deploy `firestore.indexes.json`.
4. **Listeners never stopped.** Reads keep counting after the user leaves the screen. Fix: call the function `onSnapshot` returned.
5. **Photos inside documents.** Writes fail near the 1 MiB limit. Fix: put files in Cloud Storage, store the path.
