## 10. Security rules

This skill covers the part of Firebase with the highest risk: the rules that decide who may read and write.

### Rules are your backend security

With a classic backend, authorization code runs on your server. With Firebase, the client talks to the database directly, so **security rules are the only authorization layer**. They see `request.auth` (the signed-in user), the incoming data (`request.resource`) and the existing data (`resource`). Google evaluates them on every client request.

### A first rule set

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /notes/{noteId} {
      allow read, update, delete: if request.auth != null
                                  && request.auth.uid == resource.data.owner;
      allow create: if request.auth != null
                    && request.resource.data.owner == request.auth.uid;
    }
  }
}
```

`create` is separate because on a brand-new document `resource` is null, so a combined rule would fail.

The dangerous opposite is "test mode": `allow read, write: if true;`. It makes the database public. Project templates often start there, and teams ship it. Security researchers regularly find such databases exposed. [consensus]

### Four gotchas

1. **Rules are not filters.** A query is allowed only if the rules would allow every document it could return. Query by `owner == uid` instead of "all notes".
2. **Rules do not cascade.** Allowing a collection does not allow its sub-collections, which need their own `match`.
3. **The Admin SDK bypasses rules entirely.** Server code with a service account has full access, which is why that key is so sensitive. [consensus]
4. **Lookups in rules cost reads.** `get()` and `exists()` are handy for roles and membership but add billed reads and make rules harder to reason about. [fast-moving, verify the billing detail]

### Test before you deploy

The Emulator Suite runs Firestore and its rules locally. Write a small set of allowed and denied cases and run them before every deploy, the way you would unit-test a function. It is the cheapest insurance on the platform.

### A second layer: App Check

App Check proves a request comes from your genuine app (Play Integrity, App Attest) and not a script. It is a layer **on top of** rules, never a replacement. Keep any value the user must not control (a score, a role, a balance) writable only by trusted code.
