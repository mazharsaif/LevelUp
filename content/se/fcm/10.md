## 10. Costs & safety

After this skill you can explain how Firebase charges you, estimate the cost of the Notes app before launch, set up warnings before a bill grows, and check your project against a pre-launch safety list. You will also know what you can take with you if you ever leave.

### How Firebase charges you

Every project is on one of two plans.

- **Spark** is free. You get a free quota for each product, and no payment method is needed. If you use up a quota, that product stops working until the quota resets or you upgrade. You can never be charged.
- **Blaze** is **pay-as-you-go** (you pay only for what you use). It keeps the same free quotas and charges only for usage above them. It needs a Cloud Billing account with a payment method.

Some products need Blaze. Cloud Functions do, and a new project needs Blaze to create its Cloud Storage bucket. The Notes app uses both (photos and reminder functions), so in practice it runs on Blaze.

Firebase prices most things **per operation**, not per server:

| Product | You pay for |
|---|---|
| Firestore | Reads, writes, deletes, storage |
| Storage | Stored data, downloads |
| Functions | Calls, run time, memory |
| Phone sign-in | Each SMS sent |

Firestore's free quota for reads, writes and deletes resets every day. Storage allowances work differently. Check the Firebase pricing page for the current numbers: they change, and they differ by location.

The upside: a small app costs little or nothing. The downside: cost follows **behaviour**. One careless query, run by every user many times a day, can cost more than a server. A Firestore query is billed at least one read even when it returns nothing, and a security rule that calls `get()` adds a read too.

### Estimate the Notes app

Do this before launch; it finds the expensive screen. Use letters for prices, never a number you remember. Let **P** be the price of 100,000 Firestore reads, and **F** the free reads per day. Look both up on the pricing page.

Assume 1,000 daily users. Each opens the app 3 times a day. The home screen shows their latest 50 notes with a live listener.

```text
Reads per open      = 50
Opens per day       = 1,000 x 3
                    = 3,000
Reads per day       = 3,000 x 50
                    = 150,000
Billable per day    = 150,000 - F
Cost per month      ~ 30 x
  (150,000 - F) / 100,000 x P
```

Now the same screen without `limit(50)`. Some heavy users have 2,000 notes; say the average user has 500.

```text
Reads per open      = 500
Reads per day       = 3,000 x 500
                    = 1,500,000
```

Ten times the reads, for the same screen. Listeners also add a read for each note that changes while the screen is open, and a client back from a long time offline pays for the whole query again.

What to take from it:

- The query that runs most often decides the bill. Find it first.
- Always add `limit()`, and page through the rest (see Firestore data).
- Store a count in a document instead of reading many documents to count them.

### Where surprise bills come from

Large bills rarely come from growth. They usually have one of five causes.

1. **Listeners on large queries.** A listener on all notes, kept open on an admin screen, pays for every change by every user.
2. **Loops.** A function that runs when a note is written, and then writes to that same note, triggers itself again, without end.
3. **Unbounded queries.** A query with no `limit()` grows with your data.
4. **Abuse.** Your config is public. A script can sign up and read or write in a loop. Rules limit what it touches; they do not limit how often.
5. **SMS sign-in.** Attackers request codes to expensive numbers, and you pay for each SMS. This is called **SMS pumping**.

A loop guard in a Cloud Function:

```js
import { onDocumentWritten } from
"firebase-functions/v2/firestore";

export const countWords =
  onDocumentWritten("notes/{id}",
  async (event) => {
    const after = event.data?.after;
    if (!after?.exists) return;
    const note = after.data();
    const words = note.text
      .split(/\s+/).length;
    // Stop: nothing changed
    if (note.words === words) return;
    await after.ref.update({ words });
  });
```

Without the check, each update starts the function again. Test triggers in the emulator and watch the logs for repeats.

For SMS, use phone sign-in only if you really need it. If you do, allow only the countries where your users live, using the SMS region settings in Authentication.

### Budgets, alerts and hard stops

A **budget** in Google Cloud Billing is an amount you expect to spend in a month. An **alert** emails you when actual or forecast spending passes a percentage of it, such as 50%, 90% and 100%.

Alerts do **not** stop spending. Your app keeps running and keeps costing money. Billing data also arrives with a delay, so a fast problem can grow before the email arrives.

There are two ways to stop spending automatically, both with costs:

- **Spend cap budgets.** For a few products only (Cloud Functions, App Hosting, Extensions and AI Logic), Firebase can pause that product for the rest of the month when it reaches its budget. Firestore and Storage are not on this list.
- **Disable billing by code.** The budget sends messages to a **Pub/Sub topic** (a message queue). A small function receives them and removes the billing account from the project. Google's own guide warns that this shuts down every service in the project, that resources might be deleted for good, and that it still does not guarantee you stay under budget.

For most small apps the sound setup is:

1. A budget a little above the cost you expect, with alerts at 50%, 90% and 100%.
2. Alerts sent to an inbox someone reads daily.
3. A weekly look at the Usage and billing page in the Firebase console.
4. A hard stop only for a hobby project where downtime is better than any bill.

### Pre-launch security checklist

Go through this list before you share the link.

- **Rules reviewed and tested.** Each collection has rules that check `request.auth.uid` against `ownerId`, and you have emulator tests for allowed and denied cases (see Security rules).
- **No test mode.** No rule that allows everything until a date. Search your rules files for `if true` and date checks.
- **Storage rules too.** `photos/{uid}/...` is writable only by that user, with a size and type limit.
- **App Check** added, monitored and then enforced (see Measure & protect).
- **Keys handled.** The web config is not a secret. A **service-account key** (a file that gives full admin access) never goes into the app, a repository or a chat. Prefer the default credentials of Cloud Functions over key files.
- **Auth providers limited.** Turn off sign-in methods you do not use. Check the list of authorised domains and remove old test domains.
- **Budget alerts on**, sent to a real inbox.
- **A backup tested.** You have exported data at least once and know how to restore it.

### Leaving Firebase: your exit plan

Write down how you would leave, even if you never do. It shapes choices you make now.

What you can export:

| Data | How |
|---|---|
| Firestore | `gcloud firestore export` |
| Users | `firebase auth:export` |
| Photos | `gcloud storage cp` |

```bash
firebase auth:export users.json \
  --project notes-demo
# The default bucket of the project
B=gs://notes-demo.firebasestorage.app
gcloud storage cp -r \
  "$B/photos" ./photos
```

Notes on each:

- The Firestore managed export needs Blaze and a Storage bucket. Its files are in a Google-specific format. For moving to another database, a small Admin SDK script that writes your notes as JSON is often easier to use.
- The user export includes password hashes in Firebase's own variant of **scrypt** (a password hashing method). Another system must support it, with the hash settings from the console, or users must reset their passwords.
- Photos are ordinary files and move easily.

What you would rewrite: security rules, live listeners and offline caching, function triggers, and Auth calls. To keep this small, put all Firestore and Auth calls in one module of your app, not across every screen.

### Try it

Two tasks, about 10 minutes. Neither costs money.

**Task 1: a budget alert.** This needs a project on Blaze. If you are on Spark, you cannot be charged; skip to Task 2.

1. Open the Google Cloud console and go to **Billing → Budgets & alerts**.
2. Click **Create budget**. Scope it to the `notes-demo` project.
3. Choose a specified amount that is small, for example the smallest bill you would notice.
4. Keep alerts at 50%, 90% and 100% of actual spend, and add one on forecast spend.
5. Make sure billing admins get the emails. Save.

You should see the budget in the list with 0% spent.

**Task 2: your own checklist.** Copy the pre-launch checklist into a file in your project. Mark each line "done", "not needed" with a reason, or a date. Add your cost estimate.

### Common mistakes

1. **Test-mode rules at launch.** Anyone can read all notes. Fix: owner-based rules and emulator tests.
2. **Queries without `limit()`.** Reads grow with data. Fix: limit and paginate.
3. **Self-triggering functions.** Calls and writes rise without end. Fix: exit early when nothing changed.
4. **Believing alerts stop spending.** The bill keeps growing after the email. Fix: act on alerts; use a hard stop only if downtime is acceptable.
5. **A service-account key in the app or repository.** Anyone with it has full admin access. Fix: delete the key in the console, create no new ones, use default credentials.
6. **No App Check.** Scripts use your public config freely. Fix: add App Check, monitor, enforce.
7. **Phone sign-in open to every country.** You pay for pumped SMS. Fix: allow only your users' regions, or drop phone sign-in.
8. **No export ever tried.** Data loss or leaving becomes a crisis. Fix: run an export now and keep data access in one module.

### Check yourself

1. Why does the Notes app need Blaze, and does Blaze mean you lose the free quotas?
2. Your budget alert at 100% arrives. Is the app stopped?
3. One screen reads 50 notes per open. Users open it 4 times a day. How many reads do 2,000 users cause per day?
4. Which part of the app is hardest to move away from Firebase?

**Answers.** 1. Cloud Functions and a new Storage bucket need Blaze; Blaze keeps the free quotas and charges only above them. 2. No; alerts only send email, and billing data arrives late. 3. 2,000 x 4 x 50 = 400,000 reads per day. 4. Security rules, live listeners and function triggers, because they must be rewritten; the data itself can be exported.
