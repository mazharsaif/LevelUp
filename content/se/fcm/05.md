## 5. Security rules

After this skill you can write rules that let each person read and change only their own notes, avoid the mistakes that leak data, and prove your rules work in the emulator before anyone else touches your app.

### Why rules are your only protection

In a classic app, the phone talks to your server, and your server talks to the database. The server checks every request. In a Firebase app, the phone often talks to Firestore **directly**. There is no server of yours in the middle.

So who stops a stranger? **Security rules** (a small file of conditions that Firebase checks on every read and write from a client). They run on Google's side, before any data is returned or changed.

This matters because your web config is public. Anyone can copy your project id from your web page, create their own copy of your app, and send any request they like. Your buttons and screens do not protect anything. If the rules allow a request, it succeeds, whoever sent it.

For the Notes app, the goal is simple:

- A signed-in person can create notes that carry their own uid.
- They can read, change and delete only notes they own.
- Nobody can read anyone else's notes, and signed-out visitors get nothing.

Rules are the first layer. A second layer, **App Check** (a check that requests come from your real app, not a script), is covered in Measure & protect. App Check reduces abuse, but it does not replace rules.

### Anatomy of a rule

A Firestore rules file has three parts.

```js
rules_version = '2';
service cloud.firestore {
 match /databases/{db}/documents {
  match /notes/{noteId} {
   allow read:
    if request.auth != null;
  }
 }
}
```

- **match** picks a path. `{noteId}` is a **wildcard** (a placeholder that matches any document id and gives you its value by name).
- **allow** names the operations: `read`, `write`, or the finer ones: `get`, `list` (queries), `create`, `update`, `delete`.
- **if** gives the condition. If no `allow` is true, the request is denied. Denied is the default.

Inside a condition you use three objects:

| Object | What it holds |
|---|---|
| `request.auth` | Who is asking (uid), or null |
| `resource` | The document as stored now |
| `request.resource` | The document as it would be after the write |

`resource.data.ownerId` is the owner today. `request.resource.data.ownerId` is the owner the client is trying to save. Comparing the two is how you stop someone from "stealing" a note by changing its owner.

The rule above is valid, but too weak: any signed-in person could read every note. The next section fixes that.

### Owner-only rules for the Notes app

Here is a full rules file for `notes`. It is split into two blocks for your screen, but it is one file, `firestore.rules`. First, small helper functions:

```js
rules_version = '2';
service cloud.firestore {
 match /databases/{db}/documents {
  function signedIn() {
   return request.auth != null;
  }
  function isOwner() {
   return signedIn() &&
    resource.data.ownerId ==
     request.auth.uid;
  }
  function validNote() {
   let d = request.resource.data;
   return d.text is string
    && d.text.size() <= 5000
    && d.keys().hasOnly([
     'ownerId', 'text',
     'createdAt', 'photoPath',
     'remindAt', 'reminded']);
  }
```

Then the rules for each operation:

```js
  match /notes/{noteId} {
   allow read, delete: if isOwner();
   allow create: if signedIn()
    && request.resource.data.ownerId
       == request.auth.uid
    && request.resource.data.createdAt
       == request.time
    && validNote();
   allow update: if isOwner()
    && request.resource.data.ownerId
       == resource.data.ownerId
    && validNote();
  }
 }
}
```

Why each part exists:

- **create** has no stored document yet, so it checks `request.resource`: the new note must name the caller as owner. `createdAt == request.time` forces the client to use `serverTimestamp()`, so nobody can fake the date.
- **update** checks the stored owner (`isOwner()`) and that the owner field does not change.
- **validNote()** limits the note to known fields and a sane text size. (`remindAt` and `reminded` are the two fields the reminder in Sending push uses.) Without it, a client could store megabytes of junk, and you pay for it.

### The open test mode rule

When you create a Firestore database, the console offers to start in **test mode**. It writes a rule like this:

```js
match /{document=**} {
 allow read, write:
  if request.time <
   timestamp.date(2030, 1, 1);
}
```

`{document=**}` matches every document in the database. Until the date passes, anyone on the internet can read, change or delete all your data. The console picks a date a few weeks ahead.

How projects end up shipping it:

1. Test mode makes the first demo "just work".
2. The date passes, the app breaks, and someone moves the date forward instead of writing real rules.
3. Or someone replaces it with `allow read, write: if true;` or `if request.auth != null;`. The second one feels safe, but any person who signs up can read every note.

The fix is a habit: write the owner-only rules on the same day you write your first query. Start the database in **production mode** (everything denied), and open only what each screen needs.

### Four classic gotchas

**1. Rules are not filters.** Rules do not remove forbidden documents from a result. Firestore checks whether a query *could* return a document you may not read. If it could, the whole query fails. With the rules above, this query is denied:

```js
getDocs(collection(db, "notes"));
```

This one is allowed, because every possible result belongs to the caller:

```js
query(collection(db, "notes"),
  where("ownerId", "==", user.uid));
```

**2. No cascade to subcollections.** A rule on `users/{uid}` says nothing about `users/{uid}/tokens`. Each level needs its own `allow`:

```js
match /users/{uid} {
 allow read, write: if
  request.auth.uid == uid;
 match /tokens/{tokenId} {
  allow read, write: if
   request.auth.uid == uid;
 }
}
```

**3. The Admin SDK bypasses rules.** Server code with the **Admin SDK** (the trusted server library) ignores rules completely. That is useful for Cloud Functions, but your server code must do its own checks.

**4. get() and exists() cost reads.** A rule can look up another document, such as `get(/databases/$(db)/documents/users/$(request.auth.uid))`. Each lookup is billed as a read, even when the request is denied, and there is a limit on lookups per request. Prefer data stored on the document itself, like `ownerId`.

### Rules for photos in Cloud Storage

Photos live in Cloud Storage, which has its own rules file, `storage.rules`. The idea is the same: path, operation, condition. The Notes app stores photos at `photos/{uid}/{noteId}.jpg`.

```js
rules_version = '2';
service firebase.storage {
 match /b/{bucket}/o {
  match /photos/{uid}/{file} {
   allow read, delete: if
    request.auth != null &&
    request.auth.uid == uid;
   allow create, update: if
    request.auth != null &&
    request.auth.uid == uid &&
    request.resource.size <
     5 * 1024 * 1024 &&
    request.resource.contentType
     .matches('image/.*');
  }
 }
}
```

The uid in the path must match the caller. Uploads must be images under 5 MB. Delete is separate because a delete has no `request.resource` to check. Uploading the photo from the app is shown in Functions & Hosting.

### Testing rules in the emulator

Never test rules by trying them on your live project. The **Firestore emulator** runs your rules on your own computer, with fake data and fake users.

For repeatable checks, use the official testing library **`@firebase/rules-unit-testing`** with the web SDK. It gives you `initializeTestEnvironment` and two helpers: `assertSucceeds` (the request must be allowed) and `assertFails` (it must be denied). You create pretend users with `authenticatedContext("some-uid")`, or a signed-out visitor with `unauthenticatedContext()`.

A good test set has a pair for each rule: one request that should pass and one that should fail. Test the denied cases most. A rule that allows too much never shows an error in normal use, so only a test will catch it.

Also useful: the Emulator UI has a **Requests** view that shows each request and which rule line allowed or denied it.

### Try it

You need Node.js and the Firebase CLI. A project id that starts with `demo-` keeps the emulator fully offline.

```bash
mkdir notes-rules && cd notes-rules
npm init -y
npm i -D firebase \
  @firebase/rules-unit-testing
```

Save the owner-only rules as `firestore.rules`. Create `firebase.json`:

```json
{
  "firestore": {
    "rules": "firestore.rules"
  }
}
```

Save this as `test.mjs`:

```js
import { readFileSync } from "fs";
import {
  initializeTestEnvironment,
  assertSucceeds, assertFails,
} from "@firebase/rules-unit-testing";
import {
  doc, setDoc, getDoc,
  serverTimestamp,
} from "firebase/firestore";

const env =
  await initializeTestEnvironment({
    projectId: "demo-notes",
    firestore: { rules: readFileSync(
      "firestore.rules", "utf8") },
  });
```

Then add the two checks:

```js
const ana = env
  .authenticatedContext("ana")
  .firestore();
const ben = env
  .authenticatedContext("ben")
  .firestore();
// Ana creates her own note: allowed
await assertSucceeds(setDoc(
  doc(ana, "notes/n1"), {
    ownerId: "ana", text: "Milk",
    createdAt: serverTimestamp(),
  }));
// Ben reads Ana's note: denied
await assertFails(
  getDoc(doc(ben, "notes/n1")));
console.log("Rules OK");
await env.cleanup();
```

Run it:

```bash
firebase emulators:exec \
  --project demo-notes \
  "node test.mjs"
```

You should see the emulator start, then `Rules OK`. Now break the rule: change `allow read, delete: if isOwner();` to `if signedIn();` and run again. The `assertFails` line now throws, because Ben can read Ana's note. Your test caught a leak.

### Common mistakes

- **Shipping test mode.** You see a console warning, or the app stops working on the expiry date. Fix: replace it with owner-only rules and deploy them with `firebase deploy --only firestore:rules`.
- **Querying without the owner filter.** You see "Missing or insufficient permissions" on a list screen. Fix: add `where("ownerId", "==", uid)` so the query matches the rule.
- **Using one `write` rule for everything.** Delete or create fails strangely, because `resource` or `request.resource` does not exist for that operation. Fix: split into `create`, `update` and `delete`.
- **Forgetting subcollections.** Saving a push token fails with a permission error. Fix: add a `match` for `users/{uid}/tokens/{tokenId}`.
- **Trusting the client's owner field.** Someone creates notes that claim another uid. Fix: on create, require `ownerId == request.auth.uid`.

### Check yourself

1. Why can a stranger reach your Firestore data even if your app has no "show all notes" screen?
2. In an update rule, what is the difference between `resource.data` and `request.resource.data`?
3. Your list screen runs `getDocs(collection(db, "notes"))` and fails with a permission error. Why, and what is the fix?
4. Your Cloud Function writes to a note owned by another user and it works. Is your rule broken?

**Answers.** 1. The web config is public, so anyone can send requests straight to Firestore; only the rules decide what succeeds. 2. `resource.data` is the stored document before the change; `request.resource.data` is how it would look after the write. 3. Rules are not filters: the query could return other people's notes, so it is denied as a whole; add `where("ownerId", "==", uid)`. 4. No. The Admin SDK bypasses rules, so the function's own code must check who is allowed to do what.
