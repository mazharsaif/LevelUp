## 8. Sending push

After this skill you will send push messages from a Cloud Function or your own server with the Admin SDK, in Node.js or Python. You will choose the right kind of message, send to one device or many, and clean up tokens that no longer work, so the Notes app can remind people on time.

### Sending your first message from a server

Only trusted code may send push: a Cloud Function or your own server using the **Admin SDK** (the server library with full access to your project). Never send from the app itself; that would need a secret inside the app.

You need the **token** saved in Push basics. A token from `register()` goes in the `fid` field (a **Firebase installation ID**). A registration token from the older `getToken` goes in the `token` field, which is now marked deprecated in favour of `fid`. If your SDK version has no `fid` field yet, update it.

Node.js:

```js
import { initializeApp }
  from "firebase-admin/app";
import { getMessaging }
  from "firebase-admin/messaging";
initializeApp();

const msg = {
  fid: "FID_FROM_FIRESTORE",
  notification: {
    title: "Reminder",
    body: "Tap to open your note" },
  data: { noteId: "abc123" },
};
await getMessaging().send(msg);
```

Python, the same message:

```python
import firebase_admin
from firebase_admin import messaging
firebase_admin.initialize_app()

note = messaging.Notification(
    title="Reminder",
    body="Tap to open your note")
msg = messaging.Message(
    fid="FID_FROM_FIRESTORE",
    notification=note,
    data={"noteId": "abc123"})
messaging.send(msg)
```

`send` returns a message id when FCM accepts the message. Accepted does not mean shown.

### What a message contains

Every message has exactly one **target**:

| Target | Who gets it | Use for |
|---|---|---|
| `fid` / `token` | one app install | personal alerts |
| `topic` | all subscribers | public news |
| `condition` | mix of topics | "tips and en" |

A condition combines topics, for example `"'tips' in topics && 'en' in topics"`.

Then it has a **notification** part, a **data** part, or both:

- **Notification message**: has `title` and `body`. When the app is in the background, the system shows the alert for you. Your code runs only when the user taps it.
- **Data message**: only key-value pairs, all values strings. Nothing is shown by itself; your code must decide what to show. A closed phone app may not be woken for every data message.
- **Both**: the system shows the alert in the background, and your code gets the data when the user taps it, or right away in the foreground.

For the Notes app, use **both**: the reminder always appears, and `data.noteId` opens the right note.

The whole message, including both parts, has a size limit of **4096 bytes** (the console composer allows less). Send an id, not the note. The app then loads the note from Firestore, where security rules apply.

**Never put secrets in a payload.** Messages pass through Google, Apple or browser vendors, and the text can appear on a locked screen. "You have a reminder" is safe; a password reset code or medical detail is not.

### Priority, lifespan and web options

You can add per-platform options next to the target.

**Android priority** is `normal` or `high`. High priority tries to deliver at once, even when the phone is in deep sleep (Doze). Use it only for messages the user will see right away, like a due reminder, because it uses more battery.

**TTL** (time to live) is how long FCM keeps trying if the device is offline. The default and the maximum are four weeks. A reminder for 9:00 is useless at 17:00, so give it a short TTL. A TTL of 0 means "deliver now or drop it".

**Web push options** let you set the page that opens when the user clicks the alert. The link must use HTTPS.

```js
const msg = {
  fid: "FID_FROM_FIRESTORE",
  notification: { title: "Reminder",
    body: "Tap to open your note" },
  android: {
    priority: "high",
    ttl: 60 * 60 * 1000, // ms: 1h
  },
  webpush: { fcmOptions: {
    link: "https://notes-demo" +
      ".web.app/notes/abc123" } },
};
```

In Python the same options are `messaging.AndroidConfig(priority="high", ttl=3600)` (seconds) and `messaging.WebpushConfig(fcm_options=messaging.WebpushFCMOptions(link=...))`. For Apple devices there is an `apns` block; see the Firebase docs, Cloud Messaging section.

### Topics, and when not to use them

A **topic** is a named group, such as `tips`. App installs subscribe to it, and one send reaches all of them. You do not store a token list yourself. The Admin SDK can subscribe tokens with `subscribeToTopic(tokens, "tips")`, and mobile apps can subscribe themselves.

Topics are good for public, same-for-everyone messages: "New feature: dark mode", or weather alerts per city.

Do not use topics when:

- **The message is private.** On mobile, any app install can subscribe to any topic name. A topic named after a user id leaks that user's reminders to anyone who guesses it.
- **You need per-device results.** A topic send gives you one id back, so you cannot find dead tokens.

When a token changes, its topic subscriptions do not follow it automatically. Subscribe the new token again.

### Many tokens, errors and stale tokens

To send one message to several tokens, use **`sendEachForMulticast`** in Node.js (`send_each_for_multicast` in Python). It takes a list in `fids` (or the older `tokens`) and returns one result per token, in the same order, plus `successCount` and `failureCount`. There is a maximum list size per call; check the current limit in the docs and split bigger lists.

Some sends fail because the token is dead: the app was uninstalled, or the user cleared the browser. The HTTP v1 API returns `UNREGISTERED`. The Node.js SDK reports `messaging/registration-token-not-registered`, and the Python SDK raises `messaging.UnregisteredError`. When you see it, **delete that token document**.

`INVALID_ARGUMENT` can also mean a dead token, but it often means your message is wrong. Delete the token only if you are sure the payload is valid.

Also remove tokens you have not seen for a long time. FCM treats a registration as stale after about a month without contact. A daily job can delete tokens whose `updatedAt` is older than your chosen limit.

Remember that push is **best effort**. A message can arrive late, twice, or never. Keep the truth in Firestore: the note and its reminder time live in the database, and push only says "look now".

### Worked example: send the reminder on time

Add two fields to each note: `remindAt` (a timestamp) and `reminded` (false). A scheduled function checks every few minutes for reminders that are due. Scheduled functions need the Blaze plan. Firestore will also ask for a composite index for this query; its error message includes a link to create it.

```js
import { onSchedule } from
  "firebase-functions/v2/scheduler";
import { initializeApp }
  from "firebase-admin/app";
import { getFirestore, Timestamp }
  from "firebase-admin/firestore";
import { getMessaging }
  from "firebase-admin/messaging";
initializeApp();
const db = getFirestore();
```

```js
export const sendReminders =
  onSchedule("every 5 minutes",
  async () => {
    const due = await db
      .collection("notes")
      .where("remindAt", "<=",
        Timestamp.now())
      .where("reminded", "==", false)
      .get();
    for (const n of due.docs) {
      await remind(n);
    }
  });
```

`remind` loads the owner's tokens, sends to all of them, cleans up, and marks the note done:

```js
async function remind(n) {
  const uid = n.data().ownerId;
  const snap = await db
    .collection("users").doc(uid)
    .collection("tokens").get();
  if (!snap.empty) {
    const res = await getMessaging()
      .sendEachForMulticast({
        fids: snap.docs.map(
          (d) => d.id),
        notification: {
          title: "Reminder",
          body: "Tap to see it" },
        data: { noteId: n.id },
      });
    await cleanUp(snap.docs, res);
  }
  await n.ref.update(
    { reminded: true });
}
```

```js
const GONE = "messaging/" +
  "registration-token-" +
  "not-registered";

async function cleanUp(docs, res) {
  const jobs = [];
  res.responses.forEach((r, i) => {
    if (!r.success &&
        r.error.code === GONE) {
      jobs.push(docs[i].ref.delete());
    }
  });
  await Promise.all(jobs);
}
```

Notice the body says "Tap to see it", not the note text. The real content stays behind sign-in.

### The HTTP v1 API and service accounts

Under the Admin SDK is the **FCM HTTP v1 API**, a web address that any language can call with a short-lived OAuth 2.0 access token. The older "legacy" API, which used a fixed server key, has been shut down.

The access token comes from a **service account**: a Google Cloud identity for a program, not a person. Where it lives matters:

- **In Cloud Functions**, the function already runs as a service account. `initializeApp()` with no arguments just works. No key file.
- **On your own server**, create a key in the Firebase console (Project settings, Service accounts, Generate new private key). You get a JSON file. Point the environment variable `GOOGLE_APPLICATION_CREDENTIALS` at it.

That JSON file is a full-power secret for your project, unlike the web config. Never commit it to Git, never put it in an app, and delete keys you no longer use.

### Try it

There is no FCM emulator, so this lab sends real (free) messages. Use the token from the Push basics lab and keep that page open in another tab.

1. Create a key as described above and save it **outside** any project folder, for example `~/keys/notes-demo.json`.
2. Set up a script:

```bash
mkdir send-lab && cd send-lab
npm init -y
npm install firebase-admin
export GOOGLE_APPLICATION_CREDENTIALS\
="$HOME/keys/notes-demo.json"
```

3. Write `send.mjs` with the first Node.js example, using the `token` field (the lab token came from `getToken`). Print what `send` returns, then run `node send.mjs`. You should see the alert and a message id.
4. Change a few characters of the token and run again. You get an error with a code instead of an id. Read the code: this is where the Notes app decides whether to delete a token.
5. Afterwards, delete the key in the Google Cloud console (IAM & Admin, Service accounts, Keys).

### Common mistakes

- **Sending from the client.** You put a server key in the app and anyone can spam your users. Fix: send only from a function or server.
- **Never deleting dead tokens.** `failureCount` grows every day. Fix: delete on the not-registered error and prune old tokens.
- **Data-only messages for user alerts.** Reminders sometimes never appear on closed apps. Fix: add a notification part.
- **Committing the service-account key.** Anyone with the repository controls your project. Fix: remove and delete the key at once, then create a new one kept outside the repository.
