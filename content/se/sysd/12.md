## 12. Capstone: LevelUp on a Linux server

This chapter puts everything together. You deploy LevelUp's real FastAPI server on the lab VM so that it starts at boot, restarts on crash, keeps learners' progress in a protected data directory, logs to the journal, is sandboxed and memory-capped, and is health-checked every five minutes. Then you run the same app under Supervisor to compare, and finish with the final quiz.

### The target

| Requirement | How |
| --- | --- |
| Starts at boot, after the network | `WantedBy=multi-user.target`, `After=`/`Wants=network-online.target` |
| Restarts on crash, without looping forever | `Restart=on-failure`, `RestartSec=3`, start limit 10 in 5 minutes |
| Runs unprivileged | System user `levelup` |
| Progress stored safely and persistently | `StateDirectory=levelup` → `/var/lib/levelup`, passed as `A1_DATA` |
| Logs in the journal | stdout, plus `PYTHONUNBUFFERED=1` |
| Sandboxed and capped | The chapter 7 block, `MemoryMax=300M` |
| Health-checked | A timer that calls `/api/health` |

### Step 1: install the app

```bash
sudo useradd --system --home /opt/levelup --shell /usr/sbin/nologin levelup
sudo mkdir -p /opt/levelup && sudo chown $USER /opt/levelup
# copy LevelUp into /opt/levelup (from the Mac: multipass transfer, scp or git clone)
cd /opt/levelup/server_fastapi
curl -LsSf https://astral.sh/uv/install.sh | sh && ~/.local/bin/uv sync --python /usr/bin/python3   # .venv on the system Python
sudo chown -R root:root /opt/levelup    # code is read-only to the service user
```

The server is started with `python main.py <port>` (it calls `uvicorn.run` itself) and reads its data folder from `A1_DATA`.

Why `--python /usr/bin/python3`: by default uv links the venv to a Python it downloaded into *your* home folder, and the `ProtectHome=yes` sandbox below hides home folders from the service, which would fail with 203/EXEC. Building the venv on the system Python avoids that trap.

### Step 2: the unit

`/etc/systemd/system/levelup.service`:

```ini
[Unit]
Description=LevelUp learning app (FastAPI)
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=300
StartLimitBurst=10

[Service]
Type=exec
User=levelup
Group=levelup
WorkingDirectory=/opt/levelup/server_fastapi
StateDirectory=levelup
Environment=PYTHONUNBUFFERED=1 A1_DATA=/var/lib/levelup
ExecStart=/opt/levelup/server_fastapi/.venv/bin/python main.py 8766
Restart=on-failure
RestartSec=3
TimeoutStopSec=20

# sandbox
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
CapabilityBoundingSet=
SystemCallFilter=@system-service

# limits
MemoryMax=300M
TasksMax=100

[Install]
WantedBy=multi-user.target
```

`StateDirectory=` makes `/var/lib/levelup` writable even under `ProtectSystem=strict`, so no `ReadWritePaths=` line is needed. To keep existing progress, copy the Mac's `progress/` files into `/var/lib/levelup/` and `chown -R levelup:levelup` them.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now levelup
curl -s localhost:8766/api/health
systemd-analyze security levelup
```

### Step 3: the health check

`/etc/systemd/system/levelup-health.service`:

```ini
[Unit]
Description=Restart LevelUp if /api/health stops answering

[Service]
Type=oneshot
ExecStart=/bin/sh -c 'curl -fsS --max-time 5 http://127.0.0.1:8766/api/health >/dev/null || systemctl restart levelup'
```

`/etc/systemd/system/levelup-health.timer`:

```ini
[Timer]
OnBootSec=2min
OnUnitActiveSec=5min

[Install]
WantedBy=timers.target
```

Run `sudo systemctl enable --now levelup-health.timer`. The check runs as root, so it is allowed to restart the service. Its runs appear in `journalctl -u levelup-health`.

### Step 4: prove it

1. **Crash**: `sudo kill -9 $(systemctl show -p MainPID --value levelup)`. A new PID about 3 seconds later.
2. **Reboot**: `sudo reboot`, then `systemctl is-active levelup` and `curl` the health endpoint.
3. **Logs**: `journalctl -u levelup -b` shows the kill, systemd's reaction and the restart.
4. **Hang**: `sudo kill -STOP $(systemctl show -p MainPID --value levelup)` freezes the process without killing it. Within 5 minutes the health timer restarts it. A plain `Restart=` never would, because the process never exits.
5. **Data**: use the app from your phone or browser (`http://<vm-ip>:8766`), then restart the service and check the progress is still there in `/var/lib/levelup`.

### Step 5: the same app under Supervisor

`sudo systemctl disable --now levelup levelup-health.timer`, then write `/etc/supervisor/conf.d/levelup.conf`:

```ini
[program:levelup]
command=/opt/levelup/server_fastapi/.venv/bin/python main.py 8766
directory=/opt/levelup/server_fastapi
user=levelup
environment=PYTHONUNBUFFERED="1",A1_DATA="/var/lib/levelup",HOME="/opt/levelup"
autorestart=true
startsecs=5
stopwaitsecs=20
stopasgroup=true
killasgroup=true
redirect_stderr=true
stdout_logfile=/var/log/supervisor/levelup.log
```

Run `sudo supervisorctl reread && sudo supervisorctl update`, then repeat the crash test and `tail -f`. Write down three things systemd gave you that Supervisor didn't: the sandbox, the memory limit and the journal are the obvious ones. Then switch back to the systemd unit, the recommended set-up.

**Answers.**

1. systemd; it is the parent of every service, so it sees every exit and can restart and track them.
2. SIGTERM, a grace period, then SIGKILL; `TimeoutStopSec=` and `stopwaitsecs`.
3. Both start in parallel, so the app can start before the database is ready.
4. `enable` only acts at boot; use `start` or `enable --now`.
5. `Type=exec`: a broken `ExecStart` makes the start fail instead of looking successful.
6. ExecStart isn't run by a shell, so `>>` and the path are passed as arguments; output goes to the journal anyway.
7. `on-failure`.
8. `systemctl reset-failed levelup`, then start it.
9. `journalctl -u levelup -b -p err`.
10. You must enable the timer (`backup.timer`), not the service.
11. It makes the whole filesystem read-only for the service; data goes in `StateDirectory=` or a `ReadWritePaths=` folder.
12. `supervisorctl reread` and `update`; look at the program's log (`tail x stderr`) and `supervisord.log`.
13. The container platform already supervises it, and you should run one foreground process per container; use a tiny init such as tini (`--init`) as PID 1.
14. The process never exits, so nothing triggers a restart; add a health check (a timer with curl, a watchdog, httpok or a liveness probe).
15. `~/Library/LaunchAgents/`, with `KeepAlive` set to true (and `RunAtLoad`).

Score 12 or more out of 15 and you have mastered this branch.
