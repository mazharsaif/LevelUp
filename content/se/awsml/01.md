## 1. Account, costs and safe setup

Before you learn any machine learning, make the account safe and the bill predictable. Most painful AWS stories are not about hard ML. They are about a forgotten endpoint that ran for a month, or leaked root keys.

### Why AWS has no hard spending cap

AWS bills you afterwards for what you used. There is no switch that stops everything at exactly $5. Some resources cost money just by existing: stored data, a running instance, an Elastic IP, an OpenSearch Serverless collection. Billing data also lags by several hours.

What you *can* do:

- **AWS Budgets** emails you when actual or forecast spend crosses a threshold. Two budgets are free.
- A **budget action** can apply a deny-all IAM policy or a service control policy when the budget is crossed. That blocks new activity. It does not delete anything that is already running, and it does not apply to the root user.
- **Cost Explorer** shows spend by service and by tag, so you can see which lab cost what.

The real protection is habit: use serverless or short jobs, tag everything, and delete what you create.

### Users, root and MFA

The **root user** is the email you signed up with. It can do everything, including closing the account, and no IAM policy can restrict it. Turn on MFA for root, never create root access keys, and use root only for the few tasks that need it (billing settings, closing the account).

For daily work, create a user in **IAM Identity Center** with a permission set such as `PowerUserAccess`, and sign in with that. Identity Center gives you short-lived credentials through `aws login` or `aws sso login`, so there are no long-lived access keys sitting on your laptop.

| Credential | Lifetime | Use it for |
|---|---|---|
| Root password + MFA | Permanent | Billing and account settings only |
| Identity Center / `aws login` session | Hours, renewable | Your own CLI and console work |
| IAM role (assumed) | Minutes to hours | Apps, Lambda, SageMaker jobs |
| IAM user access key | Until rotated | Avoid; legacy tools only |

### Regions and the free tier

Pick one Region and use it everywhere. This track uses **eu-central-1** (Frankfurt). Resources in other Regions are easy to forget, and the console only shows one Region at a time.

The SageMaker AI free tier lasts the first two months after you create your first SageMaker resource. It includes 250 hours of ml.t3.medium notebooks, 50 training hours and 125 real-time inference hours on ml.m5.xlarge, 150,000 seconds of serverless inference, and some Data Wrangler, Feature Store and Canvas time. So start SageMaker in week 7, not in week 1.

### Lab: make the account safe (free)

1. Sign in as root, turn on MFA, and check that no root access keys exist (IAM → Security credentials).
2. Create an IAM Identity Center user for yourself with `PowerUserAccess`. Sign out of root.
3. Configure the CLI profile: `aws configure set region eu-central-1 --profile personal`, then `aws login --profile personal`.
4. Check it with `aws sts get-caller-identity --profile personal`.
5. In Billing → Budgets, create a cost budget of $5 with alerts at 20%, 60% and 100% of actual spend, and one at 100% of forecast spend.
6. In Billing → Cost allocation tags, activate the tag key `project` once you have created a tagged resource. From now on, tag every resource `project=mla-study`.

### Cleanup checklist (use after every lab)

- SageMaker → Inference → Endpoints: none.
- SageMaker Studio → running apps and spaces: all stopped.
- Bedrock → Knowledge bases and Agents: delete finished ones.
- OpenSearch → Serverless collections: none.
- Glue jobs and interactive sessions stopped; Kinesis streams deleted.
- VPC → NAT gateways and Elastic IPs: none.
- Cost Explorer filtered by tag `project=mla-study`: under budget.

### Self-check

1. Can an IAM policy stop the root user from deleting a bucket?
2. Your budget alert fires at $5. Does AWS stop your running endpoint?
3. Why prefer Identity Center over an IAM user with access keys?
4. Which is cheaper for a demo used twice a day: a real-time endpoint or serverless inference?

**Answers.** 1: No. Root cannot be restricted by IAM policies, only by service control policies in AWS Organizations. 2: No. Alerts only notify you, and even a budget action only blocks new API calls; you must delete the endpoint. 3: The credentials are short-lived and refresh automatically, so nothing permanent can leak. 4: Serverless, because you pay only while requests run, not per hour of uptime.
