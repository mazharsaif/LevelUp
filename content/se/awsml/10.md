## 10. Evaluating ML and GenAI

This skill covers MLA-C02 Task 2.3: measuring how good a model really is, explaining it, running reproducible experiments, and evaluating generative AI and RAG systems.

### Classification metrics

From the **confusion matrix** (true positives TP, false positives FP, true negatives TN, false negatives FN):

| Metric | Formula | Use when |
|---|---|---|
| Accuracy | (TP + TN) / all | Classes are balanced |
| Precision | TP / (TP + FP) | False alarms are costly (spam filters) |
| Recall (sensitivity) | TP / (TP + FN) | Missing a positive is costly (fraud, disease) |
| F1 | Harmonic mean of precision and recall | You need one balanced number |
| ROC-AUC | Area under the true-positive-rate vs false-positive-rate curve | Comparing models across all thresholds |
| PR-AUC | Area under the precision–recall curve | Heavily imbalanced data |

The **decision threshold** (0.5 by default) trades precision against recall. Pick it from the business cost, not by habit.

### Regression metrics

- **MAE**: the average absolute error, in the target's units. It is robust to outliers.
- **RMSE**: punishes large errors more than MAE does.
- **R²**: the share of the variance explained (1 is perfect).
- **MAPE**: the average percentage error, common in forecasting.

### Baselines, explanations, debugging

- Always compare against a **baseline**: a simple rule, the previous model, or "always predict the majority class".
- **SageMaker Clarify** explains models with SHAP values (global feature importance, and a per-prediction explanation) and measures post-training bias, such as the difference in positive prediction rates between groups.
- **Convergence problems**: loss that diverges usually means the learning rate is too high; a flat loss can mean the learning rate is too low, there are vanishing gradients or the features are bad. **SageMaker Debugger** rules flag these during training.

### Reproducible experiments

- **MLflow on SageMaker AI** (managed tracking servers) logs parameters, metrics and artefacts per run, and has a model registry.
- **Amazon Bedrock Prompt Management** versions prompts, so a GenAI experiment can be repeated.
- **Amazon Bedrock evaluations** store evaluation jobs and their scores.
- Fix random seeds, version the data (S3 paths or versioning) and record the container image.

### Comparing in production

- **Shadow testing**: the new model gets a copy of live traffic but its answers are not returned to users. This is safe for comparing latency and outputs.
- **A/B testing**: production variants split real traffic (for example 90/10), and users see both models' results.
- Watch for drift against the baseline after deployment (skill 13).

### Evaluating generative AI

| Method | Measures | Notes |
|---|---|---|
| BLEU | N-gram overlap with a reference | Translation |
| ROUGE (ROUGE-1, ROUGE-L) | Overlap with a reference summary | Summarisation |
| BERTScore | Semantic similarity using embeddings | Rewards paraphrases that BLEU and ROUGE miss |
| Semantic similarity | Cosine similarity of embeddings | Quick check against expected answers |
| Perplexity | How surprised a language model is | Language-model quality |
| LLM-as-a-judge | A strong model scores outputs against a rubric | Fast, scalable; check it against human labels |
| Human evaluation | People rate helpfulness, correctness, tone | Gold standard; slow and costly |

**Bedrock Model Evaluation** offers automatic jobs (built-in or custom datasets; accuracy, robustness and toxicity), human-based jobs (your own team or AWS-managed reviewers) and LLM-as-a-judge jobs. Human-in-the-loop review at run time uses **Amazon A2I**.

Also check content quality and safety: toxicity, bias across groups, refusals and format compliance.

### Evaluating RAG

Score retrieval and generation separately:

- **Retrieval**: context relevance, context coverage, and recall or precision at k (did the right chunks come back?).
- **Generation**: faithfulness or groundedness (is the answer supported by the chunks?), answer relevance and citation correctness.
- Bedrock evaluations can evaluate a knowledge base directly (retrieve-only, or retrieve-and-generate).
- In production, log the retrieved chunk IDs and user feedback, and watch for answers with no supporting chunks.

### Lab: evaluate and explain (about $0.10)

1. From your best XGBoost model, plot the confusion matrix, the ROC and the precision–recall curve. Choose the threshold that gives at least 70% recall for "yes", and report the precision you give up.
2. Run a Clarify explainability job (SHAP) and name the top three features.
3. Track every run with local MLflow (`pip install mlflow`, then `mlflow ui`).
4. Have Nova Micro summarise 10 paragraphs, and write a reference summary for each yourself. Score them with ROUGE-L, BLEU and BERTScore (`pip install evaluate rouge_score bert_score`), then with Nova Lite as a judge using a 1–5 rubric.
5. Run a Bedrock Model Evaluation job on your 10-row JSONL as a custom dataset, and compare its scores with yours.

### Self-check

1. A cancer screening model must miss as few positives as possible. Which metric?
2. You want to compare a new model on live traffic without users seeing its output. How?
3. Which metric rewards a correct paraphrase that has few words in common with the reference?
4. A RAG bot gives fluent answers that are not in the documents. Which metric catches this?
5. Loss diverges to NaN after a few steps. Likely cause?

**Answers.** 1: Recall. 2: A shadow variant (shadow test). 3: BERTScore (or embedding similarity). 4: Faithfulness / groundedness (and a Guardrails contextual grounding check). 5: The learning rate is too high (or there are exploding gradients).
