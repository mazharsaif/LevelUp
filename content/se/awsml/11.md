## 11. Deploying models, knowledge bases and agents

This skill covers MLA-C02 Tasks 3.1 and 3.2: choosing how to serve models, provisioning the infrastructure, and deploying RAG and agents on Bedrock.

### SageMaker inference options

| Option | Fits | Key facts |
|---|---|---|
| Real-time endpoint | Steady traffic, low latency | Always-on instances; auto scaling; GPUs available |
| Serverless inference | Spiky or rare traffic; cold starts are fine | Pay per use; scales to zero; up to 6 GB memory; no GPUs |
| Asynchronous inference | Large payloads (up to 1 GB), long processing (up to an hour) | Queue-based; can scale to zero; result goes to S3 |
| Batch transform | Scoring a whole dataset offline | No endpoint left running |
| Multi-model endpoint | Many similar models with low traffic each | Models load from S3 on demand into one shared fleet |
| Multi-container endpoint / inference pipeline | Different frameworks, or pre-processing, model and post-processing in sequence | Up to 15 containers |
| Inference components | Several models on one endpoint with their own resources | Packs FMs efficiently on GPU instances |

### Bedrock deployment options

- **On-demand**: pay per token; shared capacity; simplest.
- **Cross-Region inference profiles** (for example `eu.amazon.nova-micro-v1:0`): route requests across Regions in a geography for more throughput.
- **Provisioned throughput**: reserved model units for guaranteed throughput, and for serving many custom models.
- **Batch inference**: offline JSONL jobs at a lower price.
- **Custom Model Import**: bring open-weights models (for example Llama or Mistral architectures) that you fine-tuned elsewhere, and serve them through Bedrock APIs.
- **SageMaker endpoints** instead, when you need a specific GPU instance, a custom container or full control.

### Provisioning and scaling

- Deploy with the **SageMaker Python SDK** (`model.deploy()`), **Boto3** (`create_model`, `create_endpoint_config`, `create_endpoint`) or the AWS CLI, and automate it with **CloudFormation** or the **AWS CDK**.
- **Auto scaling** with Application Auto Scaling, using target tracking on `SageMakerVariantInvocationsPerInstance`, `ConcurrentRequestsPerModel`, CPU utilisation or GPU utilisation. Scale GPU workloads on GPU utilisation or concurrency, not CPU.
- **On-demand vs provisioned**: on-demand or serverless for unpredictable traffic; provisioned capacity or Savings Plans for steady, high traffic.
- **Containers**: build images, push them to **Amazon ECR**, and run them on SageMaker, ECS, EKS or Lambda. Use AWS Deep Learning Containers as base images.
- **VPC**: put endpoints and training jobs in private subnets with security groups. Reach S3 through a gateway endpoint and other AWS APIs through interface endpoints (PrivateLink), with no internet path.

### Bedrock Knowledge Bases

1. **Data source**: S3, web crawler, Confluence, SharePoint, Salesforce or a custom source.
2. **Parsing and chunking**: default, fixed-size, hierarchical, semantic or no chunking, or a custom Lambda. Use a foundation model parser for PDFs with tables and images.
3. **Embedding model**: for example Titan Text Embeddings V2 or Cohere Embed.
4. **Vector store**: OpenSearch Serverless or managed OpenSearch (hybrid search), Aurora PostgreSQL (pgvector), S3 Vectors (cheapest), Neptune Analytics (GraphRAG), or partners such as Pinecone and MongoDB Atlas.
5. **Query**: the `Retrieve` or `RetrieveAndGenerate` APIs, with the number of results, metadata filters, hybrid or semantic search, a reranker model and query decomposition.
6. **Sync**: run an ingestion job after documents change, on a schedule or triggered by an event.

### Agents

- **Bedrock Agents**: an FM plus instructions, **action groups** (Lambda functions described by an OpenAPI or function schema), attached knowledge bases, **session attributes**, memory across sessions, Guardrails, and versions with aliases.
- **Amazon Bedrock AgentCore**: runs agents built with any framework (Strands, LangGraph, CrewAI) in production. Its parts are Runtime, Memory (short- and long-term), Gateway (turns APIs and Lambda functions into tools), Identity, a code interpreter, a browser tool and Observability.
- **Agent protocols**: the **Model Context Protocol (MCP)** connects agents to tools; **Agent2Agent (A2A)** lets agents talk to each other.
- **State management**: keep conversation and task state in agent memory, session attributes or DynamoDB. Never rely on the model alone to remember.
- **Multi-agent** setups have a supervisor agent that routes to specialist agents. Use Step Functions when the workflow must be deterministic.

### Lab: serve the model and build RAG and an agent (about $0.30)

1. Deploy the XGBoost model as a **serverless** endpoint (`ServerlessInferenceConfig(memory_size_in_mb=2048, max_concurrency=2)`). Time the first call against later calls, then delete the endpoint.
2. Run a batch transform on the test set with one ml.m5.xlarge instance.
3. Deploy two production variants (80/20) on ml.m5.xlarge with auto scaling (minimum 1, maximum 2) on invocations per instance. Send 500 requests, read the per-variant metrics, and delete everything within the hour.
4. Create a knowledge base with Titan V2, an S3 Vectors store and semantic chunking. Test `numberOfResults` at 3 and 8, a metadata filter and a reranker.
5. Create a Bedrock agent on Nova Lite with a Lambda action `days_until_exam(date)` and the knowledge base attached. Read the trace, create version 1 and an alias `prod`, then version 2, and roll `prod` back to v1.

### Self-check

1. A few requests an hour, unpredictable, lowest cost. Which inference option?
2. Inputs are 1 GB and processing takes 8 minutes. Which option?
3. Hundreds of small per-customer models with little traffic each?
4. You fine-tuned an open model on-premises and want to serve it through Bedrock. Which feature?
5. An agent must call your billing API. What do you attach?

**Answers.** 1: Serverless inference. 2: Asynchronous inference. 3: A multi-model endpoint. 4: Bedrock Custom Model Import. 5: An action group (a Lambda function with an API or function schema), or an AgentCore Gateway tool.
